# 日期处理方案审查（2026-11-01）

> 范围：本机导入、上传导入、扫描入库三条链路 + date_taken 的存储与用途。
> 依据：icloudpd 源码（`F:\iPhone\icloud_photos_downloader-master`）+ 本项目代码 + 真实库（`F:\iPhone\iCloudPhoto`，9440 张图片）只读普查。

## 一、结论速览

| 结论 | 说明 |
|---|---|
| 整体架构**合理** | 统一表示（R-08）、三环兜底、`preserveTimestamps` 都是正确取舍 |
| 需修复 ①【高】 | 上传导入不保留 mtime → 无 EXIF 文件日期错到「上传当天」（lib5 已复现） |
| 需修复 ②【中】 | 目录兜底优先于 mtime → 924 张无 EXIF 日期文件退化为「当天 00:00」，秒级时间丢失 |
| **不建议做** | 给 EXIF 链加 `0x0132` 作第三候选（真实反例证明风险大于收益） |
| 已知边界 | assetDate 缺失→1970 目录；时区无感知；目录结构非 YYYY/MM/DD 时兜底失效 |

## 二、现状盘点

### date_taken 的统一表示
- 全库统一存「本地时间 + 时区偏移」ISO8601，秒级、无毫秒，如 `2026-10-25T16:47:15+08:00`（`utils/date.ts: toLocalIso`）。
- 字符串序 = 本地时间序 = 真实顺序；`substr(date_taken,1,7)` 直接得到本地月份。

### date_taken 的 5 种用途（决定了它必须「准」且「稳定」）
1. 照片墙排序 `ORDER BY date_taken DESC, id DESC`（assets.ts）
2. 月份分组 `/api/dates` 用 `substr(date_taken,1,7)`
3. 游标分页：游标 = `base64(date_taken|id)`
4. FTS 搜索：`date_compact` 去标点日期（`toDateCompact`）
5. 详情页顶栏时间显示

### 三条日期链（现状）

| 链路 | 顺序 | 出处 |
|---|---|---|
| 扫描入库 | EXIF DateTimeOriginal→CreateDate；视频 ffprobe creation_time → **目录 YYYY/MM/DD** → mtime | scanner/index.ts:478-485 |
| 本机迁移归置 | EXIF/ffprobe → mtime（**无目录兜底**，源目录不可信） | import/resolveDate.ts:22-40 |
| 上传归置 | 同本机迁移，但 mtime = 上传落盘时刻（**缺陷**） | import/resolveDate.ts + routes/import.ts |

### 与 icloudpd 的衔接事实（源码级）
- iCloud 接口资产记录里的 `assetDate`（毫秒时间戳）是唯一时间源（photos.py:859）。
- icloudpd 用它写三处：目录 `{:%Y/%m/%d}`、文件 mtime（`os.utime`，**图片/视频/实况视频都写**）、JPEG 的 EXIF（仅当原文件无 DateTimeOriginal）。
- HEIC/视频**永不补写 EXIF**；补写失败只打 debug 日志静默跳过（已实测到 `IMG_8032.JPG` 有 EXIF 段却无日期标签）。

## 三、合理之处（应保留）

1. **统一表示（R-08）**：本地时间 + 偏移，彻底解决 UTC/本地混用导致的排序错位与跨月分组错误。
2. **目录兜底对 icloudpd 库可靠**：目录来自 assetDate，且 mtime 也来自 assetDate，两者本是一物。
3. **导入归置去掉目录兜底**：用户自维护目录结构不可信，正确。
4. **`preserveTimestamps`**：显式保留源 mtime，不赌平台默认行为（Windows CopyFile 会保留、但 FAT32/NAS/手机等不一定）。
5. **实况日期只按主资产算一次**：实况视频跟随图片进同一目录，避免跨午夜拆散配对，正确。

## 四、问题清单

### P0【高】上传导入不保留 mtime
- 现状：`routes/import.ts:96` 直接 `createWriteStream(dest)`，前端 `client.ts:363-367` 也只传了文件名，没有 `lastModified`。
- 后果：无 EXIF 日期的文件（真实库 924 张占 9.8%），`resolveDate` 落到 mtime = 上传时刻 → 归档到 `import/2026/10/31/`，date_taken 变成上传当天。
- 实证：lib5 中 `2015` 年的照片被归到 `import/2026/10/31/`，date_taken = `2026-10-31T00:00:00+08:00`。

### P1【中】目录优先于 mtime，丢秒级精度
- 现状：扫描链「目录 → mtime」，目录只到天。
- 后果：924 张无 EXIF 日期文件的 date_taken = `T00:00:00+08:00`，而它们的 mtime 其实精确到秒（已实证 924 张的 mtime 与目录 100% 同一天）。
- 例：`2015/05/03/31f76eb0….JPG` 真实 11:46:57，库里存 `2015-05-03T00:00:00+08:00`。

### P2【低】0x0132 未纳入 —— 但**不建议补**
- 事实：6 张图片只有 `0x0132`（无 0x9003/0x9004）。其中 5 张 `0x0132 == mtime`（无增量信息）；1 张 `2024/10/18/89dc0348….JPG` 的 `0x0132 = 2024:09:29`，而 mtime/目录 = 2024-10-18（**0x0132 被编辑污染，是错的**）。
- 结论：mtime（= assetDate）比 0x0132 更权威，加 0x0132 反而可能把日期改错。放弃。

### 边界情况（已知、可接受或需留意）

| 边界 | 表现 | 判定 |
|---|---|---|
| 手动复制 NTFS→NTFS | mtime 保留（Windows CopyFile 连时间一起拷），EXIF 不变 | 无影响 |
| 复制到 FAT32/U 盘/网络/手机 | mtime 可能变 | 若仍处 YYYY/MM/DD 目录，目录兜底救回「天」；挪出目录且无 EXIF → 只能 mtime（复制时刻，无解） |
| 微信/编辑软件另存 | 0x0132 可能被改、EXIF 可能被抹 | 目录/mtime 兜底接管 |
| assetDate 缺失 | icloudpd 写 1970-01-01，落到 `1970/01/01/` | 极端罕见，注意识别即可 |
| 跨时区拍摄 | EXIF 无时区按本地解释（normalizeDate），目录也按本地时区（icloudpd） | 固有局限，icloudpd 同款，可接受 |
| 目录结构非 YYYY/MM/DD（手动放文件进 icloud/） | `parseDateFromDir` 返回 null | 落到 mtime；本机迁移已走 resolveDate 无此问题 |
| 实况跨午夜 | 图片视频可能差 1 秒跨天 | 以图片为准，视频跟随，正确 |

## 五、改进方案

### 改法 C（修 P0）：上传保留 mtime
- 前端 `client.ts`：`form.append` 的同时，为每个文件附带 `lastModified`（File 对象自带，毫秒）。可用一个伴生字段（如 `mtime__<relPath>`）承载，避免改 filename 语义。
- 后端 `routes/import.ts`：先收集 `part.type==='field'` 的 mtime 映射，`pipeline` 写盘后 `fsp.utimes(dest, mtime, mtime)` 设回。
- 影响面：仅上传链路；`resolveDate` 与后续 `runScan` 自动得到正确 mtime，无需改日期链。
- 测试：加一条「上传无 EXIF 文件，断言归档目录与 date_taken 正确」的端到端用例。

### 改法 B（修 P1）：目录与 mtime 相互印证
- 扫描链（scanner/index.ts:478-485）在「目录兜底」这一步改为：
  ```
  目录日 == mtime 日  → 用 mtime（秒级精确，且两者同源互相印证）
  目录日 != mtime 日  → 用目录零点（保守，防 mtime 被复制/编辑污染）
  ```
- 影响面：仅扫描兜底分支；对 924 张文件恢复秒级，对「mtime 与目录不符」的文件行为不变（仍走目录零点）。
- 正确性依据：真实库 924 张兜底文件 mtime 与目录 100% 同一天（已普查）；且 mtime = assetDate 是 icloudpd 的确定性行为。
- 测试：scan.test.ts 增「mtime 与目录同日 → 取 mtime」「不同日 → 取目录零点」两例。

### 不做的：加 0x0132
- 见 P2，风险大于收益。

## 六、建议动作顺序

1. **先 C 后 B**，均属小改、低风险，各加 2 条单测。
2. 改完跑 `npm test`（需把新增测试文件显式加进 `server/package.json` 的 test 列表）。
3. 合并前，用 lib5 那种「上传无 EXIF 文件」的场景手工回归一次，确认不再落到上传当天。
