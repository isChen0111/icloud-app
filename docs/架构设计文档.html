1. iCloud 网页端机制 · 实测逆向结论

以下结论来自 2026-09-08 对 icloud.com.cn/photos 的实际操作（滚动 / 缩放 / 详情 / 实况 / 视频）、网络请求抓包与前端 JS bundle 源码分析（photos3 应用，2632Build19）。

1.1 照片墙网格：自研虚拟滚动 + 衍生图分级

机制实测证据对应设计启示
虚拟滚动滚动容器 grid-scroll 的 scrollHeight 达 240,255px（放大后 1,578,463px），但 DOM 中 grid-item 始终只有 ~168 个（视口内仅可见 24~36 个）。滚动跳转后立即读 DOM：items 不变、img 清空，随后按新位置重建。无 IntersectionObserver，滚动容器用自研窗口算法计算可见范围。只渲染「视口 + overscan」，不渲染全部 1.3 万项
定位方式grid-item 为 position:absolute + transform: translate(x,y)（实测 matrix 值），宽高像素级设置，父容器 grid-items 为 relative。绝对定位 + transform 平移，避免回流
列数 / 缩放滑块拖动实测：8列120px → 5列201px → 3列346px；源码常量 columnCountMin:3, columnCountMax:9, columnCountDefault:5。网格总高随列数变化（240K→585K→1,578K px）。关键：缩放全程未触发新的图片请求——同一张衍生图复用。缩放只改 CSS 布局与列数，不重载图片
缩略图加载缩略图类名 DerivativeImage，实际显示 120~346px，但 naturalWidth ≈ 415px。加载方式为 XHR → blob → URL.createObjectURL → img.src，请求打到 cvws.icloud-content.com.cn/B/<assetID>/public.jpeg?o=<签名>&v=1&x=3&a=<鉴权>（签名带过期时间）。滚动到新区域触发 ~59 个并发 XHR。单档 ~400px 缩略图覆盖全部网格缩放范围；本地可简化用 img 直连 + 磁盘缓存
请求优先级源码 offscreeniness（离屏程度）字段参与请求调度；erroredSlots 记录失败槽位并降级重试；isSizeLargeEnough(derivativeMSL, desiredSize) 选择"≥目标尺寸的最小档位"。图片加载器带优先级队列 + 失败降级
日期分组GridHeader 顶部显示当前日期；网格按拍摄时间排序连续排列；源码有独立的 SectionHeaders 类（renderSectionHeaders / arrangeSectionHeaderDOMElements）。日期作为排序键 + 独立头部层

1.2 详情页：OneUp 轮播 + 激进预加载

机制实测证据对应设计启示
轮播结构详情视图类名 OneUp / OneUpCarousel（基于 ReactSwipeCarousel），DOM 常驻 3 个 OneUpCarouselItem（前/中/后）。URL 变为 hash 路由 #/i,pz,<assetGUID>,<index>/，可前进后退、可分享定位。三格轮播 + hash 路由记录位置
大图加载详情图 naturalWidth=2048（网格 415px 的 5 倍），同样是 blob 注入；ProgressiveImageElement 带 opacity 0.3s 过渡淡入。方向键切换后，3 个 item 全部在切换完成前就已具备 2048px 大图——邻居预加载。详情档 ~2000px；预加载前后各 1~2 张
实况照片结构：静止帧 img（blob 大图）+ LivePhotosPresenter 内叠一个 <video>（同源 mp4，position:absolute; z-index:1; opacity:0; transition:opacity 500ms）+ 顶部「实况」徽标（pointer capture 区域）。实测：按住 → video opacity 变 1 并 play()（currentTime 0→2.2s）；松开 → pause() + opacity 归 0 + currentTime 归零。img + 隐藏 video 叠层，按住播放、松开重置
视频原生 <video>（videoplayer.js 为 Video.js 封装），preload="metadata"，mp4 直接流式。用 fetch 探测视频 URL 的 Range 请求：返回 HTTP 206、content-length 1024，确认基于 Range 分段流式（非 HLS 分片）。原生 video + HTTP Range 流式即可
实况/邻居预取切换轮播时抓包看到相邻项的 public.mp4 视频请求（含实况视频）被提前拉取；源码枚举了 GridAsset / GridAssetPrefetch / OneUpMainDisplay / OneUpMainDisplayPrefetch / OneUpVidComplPrefetch / OneUpNonHlsVideoPlaybackBegin 等预取分级。预取分级：按场景（网格/详情/实况）定义资源档位与时机

1.3 数据与传输层

  • 元数据：CloudKit 接口 ckdatabasews.icloud.com.cn/.../records/query 分页拉取（单次响应 24~55KB，数百条），另有 changes/zone 增量同步。→ 本地用 SQLite 单表即可，一次扫描全量入库。
  • 签名 URL：资源 URL 带 o/e/a/s 等签名参数与过期时间（实测 e=1788800643 即当前时刻），服务端鉴权后放行。→ 本地无鉴权需求，静态服务 + ETag 即可。
  • 逆地理编码：geows reverseGeocodeCoordinates 批量把 GPS 转为地名。→ 可选功能，本地可用离线库或省略。
  • HEIC 处理：iCloud 服务端把 HEIC 转码为 JPEG/WebP 衍生图（源码 isTranscoded / isTranscoderRequest 字段）。→ 本地用 sharp（libvips + libheif）做同样的转码，逻辑等价。

2. 总体架构

前后端分离的单机应用：Node.js 后端负责目录扫描、元数据入库、缩略图/视频流水线、静态资源服务；Vue 3 前端负责虚拟滚动网格、详情轮播、实况照片与视频播放。后端只读本地磁盘，不依赖任何外部服务，浏览器访问 http://localhost:8899 即可。

前端（Vue 3 + Vite）网格虚拟滚动 · 图片加载器 · OneUp 轮播 · 实况照片 · 视频播放 · Pinia 状态
⇄ HTTP / JSON
API 层（Fastify）资产查询 · 缩略图 · 视频流 · 扫描任务
⇄
服务层目录扫描与配对 · 元数据提取 · 缩略图流水线 · 视频转码 · 任务队列
⇄
数据层SQLite（better-sqlite3）· 缩略图磁盘缓存 · 原文件只读
核心设计原则：把「计算」提前到入库阶段（一次扫描生成元数据 + 按需生成缩略图），把「渲染」放到前端虚拟化（永远只渲染视口附近的几十个节点），把「带宽」降到零（本地磁盘读取，Range 流式）。

3.2 目录扫描与实况配对（关键）

iCloudPD 默认输出结构：YYYY/MM/DD/<文件名>，实况照片拆成两个文件，命名策略（默认 suffix 模式）如下：

原图类型静止帧文件实况视频文件
HEICIMG_1234.HEICIMG_1234_HEVC.MOV
JPEGIMG_1234.JPGIMG_1234.MOV
配对规则：扫描时对每个文件计算「去后缀 + 去 _HEVC 后缀」后的基名，基名相同且位于同一目录内且一个为图片（HEIC/JPG/PNG…）一个为视频（MOV/MP4…）即配对为实况照片（iCloudPD 的 suffix 命名天然保证一一对应，无时间差校验）。视频不带静态帧配对的即为普通视频。
⚠️ 跨目录同名文件坑（重要，2026-09-08 修复）
现象：iCloudPD 会把不同设备 / 编辑版本的同名文件（如 IMG_0040）按各自拍摄日期归档进不同目录——实测库中存在 2018/02/04/IMG_0040.HEIC + IMG_0040_HEVC.MOV 与 2021/07/27/IMG_0040.MOV 这类跨目录同名组（全库共 2,363 个基名分布在多个目录）。早期扫描按「文件名基名」配对，跨目录同名被合并成一组，代码只取 videos[0] 配对实况，同组其余视频被静默丢弃，且实况视频可能配到另一张同名照片上。这里的“只取第一个视频”是旧行为；当前实现会把同组额外视频作为独立视频资产保留。
实测影响：磁盘 10,609 个视频文件只入库 7,228，丢失 3,382 个视频（含 1,799 个实况配对视频 + 1,582 个独立视频）；同时 1,799 张实况照片因跨目录被误记为普通照片。
修复：① 配对 key 从「文件名基名」改为「目录 + 基名」，配对只在同一目录内进行；② 增量扫描从「已入库直接跳过」改为「复用现有元数据、仍执行 UPSERT 修正 type/live_video」，保证重扫时旧数据能按新配对规则归位。
重扫验证：photo 1,982 + live 7,434 + video 3,175 = 12,591，与磁盘文件数精确一致（10,609 视频全部入库）；与 iCloud 网页端统计基本对齐（iCloud 照片 9,419 ≈ 本地 9,416，视频 3,033 ≈ 本地独立视频 3,175）。

增量设计：以 file_path 为唯一键 UPSERT（无 checksum 比对）；已入库文件复用现有元数据、仅修正 type/live_video（配对规则变更后重扫即可生效，无需清库）。媒体类型以支持的扩展名识别；隐藏目录忽略，但隐藏媒体文件仍会检查扩展名。对文件名恰为扩展名的合法文件（如 .mp4），在 Node 将其视为 dotfile、path.extname() 返回空字符串时仍按媒体类型收录。扫描优先依据常见的 YYYY/MM/DD 目录日期处理较新的媒体；这只是处理优先级，入库和照片墙展示仍按 EXIF/ffprobe 得到的实际拍摄时间排序。没有可识别目录日期的文件排在有日期文件之后，不会被跳过。全量扫描时间主要取决于媒体元数据读取和磁盘性能。

3.4 缩略图流水线

参照 iCloud 的「档位 + 按需」模型，定义 grid 与 detail 两档缩略图，视频另生成 poster：

档位规格用途全量估算
grid最长边 320px，WebP q80网格任意缩放级别复用（实测 iCloud 415px 档覆盖 120~346px）~25KB/张 × 12,591 ≈ 0.31GB
detail最长边 1600px，WebP q82详情页大图（对标 iCloud 2048 档，本地 1600 已足够）~250KB/张 ≈ 3GB（可仅按需生成最近浏览的）
video posterffmpeg 优先抽第 1 秒帧；短视频按时长选择片段内时间点，无帧时回退到开头 → 320px WebP视频缩略图~60KB × 3,175 ≈ 0.19GB

生成策略：缩略图按请求惰性生成，并由后台队列补齐缓存。前端请求某张缩略图 → 后端查缓存未命中 → 生成并写入磁盘缓存（ETag 缓存到浏览器）；扫描后待生成资产只将 grid 档加入后台队列。后台补图与照片墙、搜索及详情触发的交互任务共享最多 8 个并发槽位：空闲时后台可使用全部槽位；浏览活动期间暂停派发新的后台任务，已启动的任务不强制中断，释放的槽位优先给交互请求；停止活动 30 秒后后台恢复。照片墙慢速滚动和滚轮操作持续懒加载，浏览器侧最多并发派发 8 个网格图请求；拖动浏览器滚动条时每 250ms 检查一次位移，仅当位移不超过约 1/5 屏时派发当前可视区请求，快速跨屏时跳过中间经过的位置，停止移动后继续派发当前位置；松开后等待 180ms，再按最终视口及一行邻近范围排序、逐张补位加载。日期导航跳转立即加载，不经过滚动条拖动延迟。扫描流程不受该调度影响。Sharp 全局并发限制为 2，视频/HEIC 后台抽帧的 FFmpeg 解码线程限制为 1（交互任务为 2）。照片墙格子接近视口时请求 grid，图片加载完成前显示稳定的底色占位，成功加载后淡入。同一资产、同一档位的并发生成由 in-flight Map 去重。

调度器实现（F-01/F-02 落地 2026-10-06，server/src/pipeline/thumbnailScheduler.ts）：单一 p-queue 统一管理交互与后台任务——priority 10 = 交互（浏览中的图插队先跑）、priority 0 = 后台（浏览租约 30s 内挂起，到期放行）；总并发 = config.thumbConcurrency（默认 8），旧双队列（后台 8 + 交互 1 = 9 并发）合并后严格 ≤ 8，单元测试 9/9 覆盖并发不变量 / 插队 / 租约 / 积压 / 队列指标。F-02 轻量版：/api/thumb 与 /api/video/poster 任务开始执行时检查 req.raw.destroyed / aborted，断开则跳过生成并计入「已跳过」（cancelled）。/api/stats 新增 thumbConcurrency（前端调度器并发上限的唯一来源，防前后端漂移）与 thumbQueueMetrics { running, interactiveRunning, interactiveWaiting, cancelled }（诊断指标）。前端调度器（web/src/composables/gridThumbnailScheduler.ts）挂载后从 /api/stats 校准并发上限，滚动触发经 rAF 合并。完整机制见 4.12。
性能取舍：移除独立 blur 档：blur 小图虽小，生成时仍需读取、解码源媒体并缩放/编码；若与 grid 到达间隔很短，额外占位的视觉收益有限。本实现已移除独立 blur 档：后台队列只预热 grid，格子先显示底色，待 grid 图片加载成功后淡入；扫描时会清理旧的 cache/thumbs/blur/ 缓存。详情页仍可复用 grid 图并通过 CSS 模糊作为临时占位，不会额外生成或请求 blur 文件。

3.5 视频播放与转码（关键风险点）

实测更新：本机 Chrome 可直接播放 HEVC/H.265 的 MOV（策略 A 原片直出 + Range 206 已验证，进度条拖动、时长、实况视频播放均正常）。若目标机器缺失系统 HEVC 扩展导致黑屏，再启用策略 B 转码兜底。
策略做法评价
A. 原片直出（推荐起步）/api/video/:id/stream 直接流式原 MOV + Range。前端 <video> 播放，若 error 事件（编码不支持）则提示装 HEVC 扩展或切转码版零转码成本，先跑通
B. 按需转码缓存（推荐最终态）播放时检测编码：非 H.264 则后台任务用 ffmpeg 转 H.264（-c:v libx264 -preset veryfast -crf 23），产物存 cache/transcoded/，前端回退到 /api/video/:id/stream?variant=h264首次播放需等转码（可转 360p 预览先行）；有硬件编码（qsv/nvenc）可加速
C. 全量预转码入库后后台批量转全部 3,175 个视频150GB 原片转码耗时数小时~天级，资源消耗大；不推荐首版

实况照片视频同样走此通道（HEVC 兼容问题一致）；由于实况视频通常仅 2~5 秒，按需转码极快，体验无损。

4.3 图片加载器（对标 DerivativeImage）

  • 两级缓存：内存 LRU（上限 ~300MB，存最近浏览的 blob）+ 浏览器 HTTP 缓存（后端 ETag）。

4.8 P2 搜索：FTS5 trigram 全文搜索（已落地）

  • 索引：assets_fts 是 trigram 分词器虚拟表（修复审查 F-06，2026-10-06：不再每次启动 DROP+CREATE——建表改 CREATE VIRTUAL TABLE IF NOT EXISTS，结构版本由 PRAGMA user_version 记录（FTS_SCHEMA_VERSION，列变更才 bump）：版本不符才 DROP+CREATE 重建，版本一致时只按行数差回填（新增资产场景），正常启动零重建）。三列：search_text（小写文件名）/ date_taken（原始 ISO，支持搜 "2024-09" 按年宽匹配）/ date_compact（去标点 "20240913T084028"，支持搜 "202409"）。
  • 查询清洗：小写 + 非中英文数字统一转空格 + 丢弃 <3 字符 token（trigram 最小 3 字符）——避免 FTS5 语法特殊字符（引号/括号/AND 等）破坏 MATCH、日期 "-" 被误读为列分隔符。
  • 路由：GET /api/search?q=&limit=&offset=（防抖 300ms，Esc/清除退出回照片墙，点结果进同一详情路由）。搜索结果照片墙化（2026-09-19）：匹配集 = 按拍摄时间倒序的资产流，响应返回 total（真实匹配计数）+ months（匹配集月份分组，与 /api/dates 同构）+ offset 跳页分页；前端 search store 实现与 assets store 同构的 GridDataSource 接口，GridScroller 抽象后照片墙与搜索共用同一虚拟滚动模型（月份头行 / 吸顶日期跨度 / 列数滑块共享，组件实例不销毁只切数据源）——搜索结果不再固定 100 条截断，几千条匹配集同样流畅滚动。
  • ⚠ trigram 精确性兜底（2026-09-19）：FTS5 trigram 对多字符查询按「片段 AND」匹配（"2023" → "202"+"023"，带引号短语也无相邻约束，实测与 "202" AND "023" 结果一致）——日期时间串碰巧同时含两片段即误命中（搜「2023」曾混入 2018/2021/2025 年照片，如紧凑时间 20181207T120239 的 T1202→202 + 0239→023）。修复：FTS 只做粗筛（走索引超集），对每个查询 token 追加连续子串精筛 instr(lower(filename), t) OR instr(date_taken, t) OR instr(replace(date_taken,'-',''), t)，多 token 逐词 AND。实测 2131 → 2126 = 库中 2023 年资产数，误匹配归零，1ms。
  • 错误处理分类（修复审查 F-05，2026-10-06）：旧实现 catch 吞掉所有错误返回空结果——DB 错误/FTS 表损坏等真异常会伪装成「没有找到匹配」。现按错误类型分类：清洗后仍由畸形输入触发的 FTS 语法类错误（消息含 syntax/malformed/no such column 等）→ 仍返回空结果（输入问题）；其余真异常 → 返回 500 + 错误信息。前端 search store 新增 searchError：首屏（offset 0）请求失败置错（换词/成功自动清除），GridView 搜索提示条显示「搜索失败，请重试」+ 重试按钮（重新 init）；滚动中后续页失败仍走「静默 + 滚回重试」，不受影响。

4.9 P2+-1 目录热监听 + 删除对账 + 启动同步（已落地，一键拉取仍待开发）

  • 热监听（scanner/watcher.ts）：chokidar 监听 iCloudPhoto/ 目录树——ignoreInitial（启动时已有文件不触发，由启动同步负责）+ awaitWriteFinish 2s（拷贝完成才视为落盘）+ 忽略隐藏文件；add/change/unlink/unlinkDir 任一事件 → 防抖 1.5s 合并 → 触发一次 runScan('watcher')（幂等增量）。扫描互斥：扫描中延后 2s 补一次（dirty 标志）。
  • 删除/配对对账：runScan 末尾按配对后的主资产路径核对 DB——只有根目录和所有可见子目录都成功读取时才清理已删除资产，或清除已从独立视频转为实况附件的旧视频记录及 FTS/缩略图缓存；配对 MOV 仍在磁盘但不作为照片墙独立资产。任一目录读取失败则保留数据库记录并跳过本次对账。完整扫描后再清理孤儿缩略图。
  • 启动同步：index.ts 启动即后台 runScan('startup')（不 await 不阻塞），手动拷入的文件开机即被发现。
  • 扫描期间刷新：前端保留每 5 秒一次的 /api/stats 轮询，但扫描期间不因资产数变化自动刷新照片墙，避免清空已加载页并导致格子/缩略图反复重载；用户可手动刷新查看已入库内容。扫描完成或失败后自动做一次最终刷新，并尽量保留滚动位置。为避免事件推送和高频重查带来额外复杂度，当前不使用 WebSocket/SSE。
  • 顶部资源状态：顶栏保持单行摘要（状态 + 照片/视频数），点击后展开浮层详情，不改变照片墙布局高度。扫描中显示旋转图标、已检查媒体文件数和当前已入库资产数；扫描完成显示勾号及最终文件数；失败用警告状态和错误说明。照片和视频计数口径通过计数旁的悬浮提示说明：照片数包含普通照片和实况照片，视频数不含实况配对 MOV。
  • 预览图任务统计口径：扫描期间不显示预览图百分比/总量，可提示浏览中的项目按需生成、其余扫描后入队。删除对账完成后，进度从资产表持久化状态初始化：全库资产数为总量，thumb_status='done' 为已生成，pending 为待处理；所有 error 项计入已处理，未忽略的失败计入失败提示。成功/失败的队列任务结束时递增已处理，百分比 = 已处理 / 全库总量，因此服务重启后会从数据库恢复已生成进度，新入库资产也会进入总量。忽略项不再计入待处理提醒；重试会将其重新入队。/api/stats 的 thumbnails 返回 status/total/processed/completed/pending/failed。扫描结束段执行缓存对账（F-07 系列）：grid 缩略图已存在但 DB 仍 pending 的资产直接补记 done（不入队），再统计真实待处理入队——根治「缓存已生成但状态未同步」导致的待处理永不收敛（99% 转圈死锁）。
  • 浏览优先的预览图调度（F-01 修复后）：单一 p-queue 共享并发预算（默认 8），交互任务 priority=10 插队、后台任务 priority=0；前端可见时的滚动、点击、键盘、触屏及输入操作每 10 秒至多发送一次 POST /api/thumbnails/activity，每次续租 30 秒。租约内新后台任务挂起（deferred）不派发，当前正在运行的任务允许完成；挂起超过 60 秒（backgroundMaxDeferMs）的任务即使仍在租约内也强制放行（防持续浏览饿死后台、保证进度收敛）。用户通过照片墙、搜索、详情页触发的 grid/detail 请求走交互优先级。扫描/元数据入库流程保持原样。后台视频和 HEIC 的 ffmpeg 解码线程限制为 1（交互任务为 2）。
  • 顶部状态交互实现：默认只显示一行摘要；详情浮层分“照片库扫描”和“预览图准备”两行。扫描中的预览图行不展示进度；扫描结束后再展示处理进度条与已处理、已生成、待处理、失败数量。失败入口三态（F-07 系列）：有未忽略失败显示「失败 N 项 ›」，无失败但有忽略项显示「已忽略 N 项 ›」（入口常驻，保证忽略清单始终可管理），都没有显示「失败 0」。打开失败清单可查看文件路径和失败原因、逐项或批量重试、忽略/恢复提醒。忽略仅关闭失败提醒，不会删除源文件；旧记录若没有持久化错误原因会明确显示未记录。服务重启时根据数据库中 done/pending/error 状态恢复全库累计进度；每次统计轮询按数据库当前未忽略的失败状态同步失败数，已生成数来自持久化 done 状态。没有待生成任务时显示“预览图已就绪”。
  • 失败记录与恢复 API：assets.thumb_error 记录最近一次网格预览图生成失败原因（最长 1000 字符），thumb_ignored 持久化用户的忽略状态；既有数据库启动时通过列检查补齐字段，旧失败记录没有原因时由 UI 提示“失败时未记录详细原因”。GET /api/thumbnails/failed 返回失败与已忽略失败项；POST /api/thumbnails/retry 支持指定 ID 或全部失败项；POST /api/thumbnails/ignore 支持忽略或恢复提醒。仅扫描中返回 409（preparing 不再锁操作——忽略/重试与批处理并发安全，曾出现 preparing 被浏览租约挂起拖久导致失败项操作全部 409 的死锁）。
  • 临时帧回收：视频/HEIC 缩略图生成时使用 cache/tmp/ 下的 PNG 临时帧，正常完成后即时删除；后端启动时额外清理符合流水线文件名规则且超过 24 小时的残留文件。

4.12 照片墙滚动 → 缩略图请求的前后端协同机制（三道闸 + F-01/F-02，2026-10-06）

照片墙缩略图请求在「前端 → 网络 → 后端」链路中被三层机制逐级过滤，目标只有一个：离屏 / 已失效的请求尽量不占用生成资源，正在看的图永远最优先。

  • 闸 1 · IntersectionObserver（useLazyImage.ts）：每个格子挂 IO，rootMargin 300px 预热、threshold 0.01——格子未进入视口 300px 范围内就不设置 img src，不发请求（快速滚过的大多数图浏览器层面零请求，最有效的一道闸）。
  • 闸 2 · 前端调度器（gridThumbnailScheduler.ts）：pending / active 两级 Map；并发上限默认 8，挂载后经 /api/stats.thumbConcurrency 校准（后端 config 唯一来源，防漂移）。pump() 排序「可见优先 → 距视口近优先」；滚动触发经 rAF 合并（每帧最多一次 pump，避免 scroll 风暴中每帧 getBoundingClientRect 强制布局重算掉帧）；拖滚动条 250ms 节流：位移 ≤ 1/5 视口才加载真可见格子，快速跨屏跳过中间位置；松开后 180ms settle 再按最终视口补位；日期跳转走 prioritizeNextScroll() 立即加载。格子销毁时 cancel 移除 pending / active 并补发。
  • 闸 3 · 后端调度器（thumbnailScheduler.ts，F-01 修复核心）：单一 p-queue，concurrency = config.thumbConcurrency（默认 8），任务分 交互 priority=10 / 后台 priority=0；浏览租约 markBrowsing 起 30s 内后台任务挂起（deferred），租约到期统一放行。旧双队列（后台 8 + 交互 1 = 9 并发）合并后总并发严格 ≤ 8，交互插队先跑。
  • F-02 检查点（轻量版）：/api/thumb/:id 与 /api/video/:id/poster 的任务在「开始执行那一刻」检查 req.raw.destroyed || req.raw.aborted，已断开 → 跳过生成 + 计入「已跳过」（cancelled），静默结束、不进失败清单。局限：只拦「排队期间已断开」的请求，运行中断开不拦（完整版做任务撤销 / 运行中检查，暂缓）。
  • 协同效应与空转（重要结论）：闸 2 限流（≤8 并发）→ 后端交互队列几乎永不排队 → F-02 拦截窗口（排队中断开）≈ 不存在——日常滚动「已跳过」恒为 0 是预期行为。F-02 定位 = 纵深防御（前端调度器异常时兜底）+ 极端积压保险（全量重建 + 浏览、慢任务占满槽位时）。诊断指标 /api/stats.thumbQueueMetrics { running, interactiveRunning, interactiveWaiting, cancelled } 已落地。
  • 浏览信号闭环：App.vue 监听 pointerdown / wheel / keydown / touchstart / input → notifyThumbnailBrowsing()（10s 节流）→ 后端 markThumbnailBrowsing → 30s 租约；缩略图请求本身也标记浏览（双通道幂等，覆盖「人在浏览但图全缓存」场景）。
  • 缓存与失效：缩略图响应 Cache-Control: max-age=1y + ETag（mtime+size），前端 URL 带 rev 版本参数——内容修复后改 rev 强制刷新；代价：服务端文件缺失时浏览器用旧缓存不自愈（强刷 / rev 变更可恢复）。

9.1 广色域 HEIC 与 Web 显示颜色差异（2026-09-21 实测）

现象：同一张 Display P3 HEIC（例如 IMG_7935.HEIC）在 Windows“照片”查看状态和 iCloud 官网中颜色更鲜明；本项目生成的 WebP 以及部分普通图片应用中颜色偏淡。该差异目前记录为已知问题，暂不强行校正。

已确认的处理链：

HEIC（含 Display P3 原色与约 536 bytes ICC）
  → FFmpeg/libheif 解码
  → PNG 临时文件（像素转为 RGB，但默认导出会丢失明确的 P3 ICC 标识）
  → Sharp 缩放
  → WebP 缓存（详情最长边 1600px）

已确认的事实：

  • FFmpeg 读取原始 HEIC 时报告 color_primaries=smpte432（Display P3）、color_trc=bt709、color_space=smpte170m，并检测到 536 bytes ICC。
  • 当前 FFmpeg 默认输出 PNG 的报告为 rgb24(pc, gbr/unknown/unknown)；Sharp 读取该 PNG 时没有 ICC。不能把 Sharp 的 space: srgb 报告当作已完成 P3→sRGB 转换的证据。
  • 仅使用 keepIccProfile() 不能恢复已经在 FFmpeg 输出阶段丢失的源 Profile；将源 ICC 事后附加到 PNG，再调用 toColorspace('srgb') 也没有实测复现 iCloud/Windows“照片”颜色。
  • 已排除浏览器缓存、前端加载状态透明度、单纯 JPEG 中间压缩和单纯 WebP 质量设置是主要原因。

当前取舍：保留可明确说明作用的改动：HEIC 中间文件使用 PNG 以避免额外 JPEG 有损压缩；普通图片和视频帧尽量保留已有 ICC；缩略图 URL 版本递增以刷新旧缓存。撤销未经验证的 HEIC ICC 重挂载和 P3→sRGB 实验代码。后续若修复，应在 FFmpeg 阶段明确选择“正确转换为 sRGB”或“保留 Display P3 并写入匹配 ICC”，并用原始 HEIC、FFmpeg 输出、最终 WebP 三阶段产物和元数据进行回归对照，不能靠提高饱和度猜测修复。
