## 一、现状

### 1.1 这个项目是什么

本地网页应用，复刻 iCloud 网页端的照片浏览体验，数据全在本机。

- 后端 `server/`：Node 24 + TypeScript + Fastify 5 + better-sqlite3，监听 **0.0.0.0:8899**
- 前端 `web/`：Vue 3.5 + Vite + TypeScript + Pinia + vue-router(hash)，**5173**（Vite 绑 IPv6，勿用 `127.0.0.1:5173`）
- 两个照片来源：**iCloudPD 下载**（`icloud/`）与**用户本地目录导入**（`import/`），统一扫描入库、统一浏览
- 版本管理：私有仓库 + GitHub `isChen0111/icloud-app`，SSH 推送；`git push origin main`

能力范围：虚拟滚动照片墙（4~12 列）、月份跳转、详情轮播与渐进显示（复用 grid 图做 CSS 模糊占位再淡入）、实况照片按住播放、视频 Range 播放、FTS5 搜索（文件名/日期子串）、深浅主题、客户端删除（照片墙单选/多选 + 详情页）、缩略图失败清单（重试/忽略/恢复提醒）、目录热监听 + 删除对账 + 启动自动同步、多照片库（创建/切换/删除/链接 iCloud/全量拉取/增量同步）、导入本地目录（本机迁移/上传）。

### 1.2 库结构（2026-10-31 改过，别无意识按旧理解）

```
<仓库根>\                      # 路径相对描述，不绑定盘符；仓库可随时删掉重 clone
├─ PhotoLib\lib<id>\           # library_root，每个库一个目录
│  ├─ icloud\                  # icloudpd 下载目标（--directory 指向这里），YYYY/MM/DD
│  └─ import\                  # 用户导入，重排为 YYYY/MM/DD
└─ server\cache\
   ├─ meta.db                  # 库注册表（多库共享，不随激活库切换）
   └─ lib<id>\                 # 各库 library.db / thumbs / cookies
```

- **两个子树必须物理隔离**：icloudpd 增量同步用 `--until-found` 比对，它只看 `icloud/`。混放会让无关文件干扰增量判断。
- **库目录是程序独占的数据目录**：设置中心展示路径 + 复制按钮只为人自己翻找或备份，**写入必须走导入**。手放文件会绕过判重、日期与补写逻辑，产生副本和错日期。
- **单活跃库模型**：同一时刻只有一个库 `active=1`，扫描、同步、导入都作用于激活库。**切库 = 后端热切换 + 前端就地重建**（`App.vue` 的 `applyLibrarySwitch`，不刷新页面，所以设置页能留在原地）；**删激活库**仍走整页 `location.reload()`（删完可能回无库/换库，注册表与路由都变了，重建成本远高于刷新）。

### 1.3 数据与运行

- **工作区布局（2026-11-04 迁移后）**：工作区根 `F:\Agent Program\icloud-app-agent\`，内含 `icloud-app\`（本仓库，删掉重 clone 即可恢复）、`iCloudPhoto\`（**正式照片数据**）、`TestPhotoLib\`（测试照片暂存）、`iCloudTool\`（icloudpd 等工具）、`.workbuddy\`（AI 工作区记忆，只留指路页）。
- **正式照片数据在工作区根的 `iCloudPhoto\`**（万级媒体文件）。它在仓库之外、工作区之内，**同样禁止一切写操作、扫描、清理、删除**；能碰它的只有「迁回正式数据」这一条路（见下）。
- 2026-11-04 照片库根目录由 `iCloudPhoto` 改名为 **`PhotoLib`**，同时清空了全部测试库。当前无任何库，等用户重建并迁入正式数据。
- 工作区根的 `TestPhotoLib\` 与仓库内的一切（`PhotoLib\`、`server\cache\`）都是可弃测试数据，可随便造/删。
- 迁回正式数据：**先停后端 → 复制进 `icloud/` → 再启动**，让 `runScan('startup')` 一次对账。否则 chokidar 会为每个新文件排 2 秒 `awaitWriteFinish`，几万文件就是事件洪峰。迁入前用户会先清掉现有测试数据。
- **后端是 `tsx watch` 起的**：改后端代码即热重启，启动迁移会**立刻对真实库生效**。凡「要先备份再迁移」的改动，先请用户停后端。
- 测试现状：后端 `npm test` **178 例**；前端 **0 例**（全靠手工验收）。

### 1.4 关键口径

- **照片数含实况照片**；**视频数不含实况配对 MOV**（它在配对时被并进 photo 那条记录的 `live_video`）。
- **`date_taken` = 本地时间 + 时区偏移**，秒级无毫秒（`2026-10-25T16:47:15+08:00`）。字符串序 = 本地时间序 = 真实顺序，`substr(date_taken,1,7)` 直接得本地月份。
- **`scan.assetsFound` ≠ `scan.assetsAdded`**：前者是「本轮处理过多少」（含签名未变直接跳过的老资产），后者是「本轮新入库多少」。浮层「新增 N 项」只能用后者。
- 具体资产数、体积、文件名属个人隐私，文档里一律写「万级 / 数千级」这类等级描述，不写精确值。

| 2026-11-01 | 判重**只比 mtime**（1ms 容差），不比 size、不哈希 | 关键在先落位后补写 EXIF：补写会**改变文件字节数**（实测 274 → 3445），落盘后的 size 与源文件不再相等。若按「同名 + size + mtime」三键判重，第二次导入同一批文件必然判成「内容不同的另一个文件」→ 每重导一次多一份 `(n)` 副本，且 `skipped` 计数永远不涨。mtime 本来就是本项目「拍摄时间的载体」（无 EXIF 文件的日期来源），拿它当同名文件的唯一区分键语义正好。代价：同名 + mtime 毫秒级精确相同 + 内容不同会误判，但要同时满足这三条基本只剩「原地改内容却保留 mtime」，本项目不会产生这种状态。全库 sha256 对几万文件成本不可接受；纯文件名更不行（同名满世界） |
| 2026-10-31 | 补写 EXIF **只写 0x9003 / 0x9004** | `0x0132 (ModifyDate)` 有反例，写了会让排序错乱。加 `-P` 保 mtime，写完复读校验，必要时 `utimesSync` 回设 |
| 2026-10-31 | 补写放在**导入**，不放扫描 | 扫描发生在用户手上已有的目录；改人家的文件必须有明确的用户动作，导入就是那个动作 |
| 2026-10-31 | 去掉「补写 EXIF」复选框，默认始终补写 | 这个决定用户没有任何判断依据，给开关只是把负担转嫁出去 |
| 2026-11-01 | 库目录定性「**程序独占、应用内只读**」 | 展示目录是为了让人能翻找/备份，不是鼓励手放文件。文案与 UI 都要按这个定性走 |
| 2026-11-01 | 加**源目录守卫**（六种拒绝） | 误选库根或磁盘根会导出重复副本甚至把库导进自己。用 `realpathSync` 解 junction + Windows 折叠大小写做双向包含判断 |

| 2026-11-03 | 认证启动前**清理无主 cookie 的半成品 `.session`** | icloudpd 只要看到 `.session` 就尝试续会话（不需要密码），直接跳到验证码。认证中途取消会留下这种残骸，于是「没登录过却直接从验证码开始」。只删「没有主 cookie 陪跑」的 `.session`；主 cookie 完整时它是正常续期凭据，删了会逼用户重走完整登录 |
| 2026-11-03 | 导入做成**与同步同级的一等任务**：顶栏摘要带百分比、状态浮层独立一行 + 进度条 + 「查看导入详情 / 取消导入」 | 导入弹窗可关，但**关窗 ≠ 取消**（后端流水线照跑，几万张能跑几十分钟）。此前关窗后只剩顶栏一句「正在归置新照片」，没有总数与进度，用户以为任务停了。长任务的进度与取消入口必须挂在**不会被关掉**的常驻位置（顶栏/浮层），弹窗只当「详情视图」。设置页「导入照片」按钮同样按库显示进度百分比 |
| 2026-11-03 | 扫描**稳态跳过写库**：签名（size+mtime）与 `type`/`live_video` 三项都没变时，不 UPSERT、不重写 FTS | 每轮扫描原本无条件写 13 列 + `INSERT OR REPLACE` 进 FTS，文件没变也写。跳过条件必须含 `type`/`live_video` —— 13 列里只有这两列有「修正语义」（配对按「目录+基名」每轮重算），其余元数据取自库、写回是空操作。**但 `file_size IS NULL` 的历史行必须仍写库**：它们 `changed` 恒为 false，唯一补签名的途径就是这条写库路径，跳过 = 永久失去内容变化检测。20k 库一轮从「遍历 + N 次写库」降到「遍历 + stat」 |
| 2026-11-03 | 导入归置期间**周期扫描**（每 100 个文件 且 至少间隔 20 秒 → `runScan('import')`） | 原实现归置全程零扫描，几万张要等几十分钟才有第一张上墙，「边导边看」只对同步成立。阈值取「且」不取「或」：只看文件数会被快盘绕过（几秒一轮，照片墙反复重建），只看时间会做无用扫描；时间控节奏、文件数防抖。**不能重新开 watcher 来代替**：`awaitWriteFinish` 为每个待确认文件每 100ms 轮询一次连查 2s，每秒落几百个文件时是上万次 stat，且事件不停会把防抖无限重置。60 秒的间隔意味着用户对着空墙等一分钟，故选 20 秒 |
| 2026-11-03 | 状态浮层**只加不减**：新增同步行、扫描行落库中显示「已入库 N 项」、完成态补「· 新增 M 项」、完成态图标改绿底；不改成 v1 的「单一主进度 + 阶段机」 | v1 的线性阶段会与事实不符——下载/入库/预览图是**并行**的（第 N 批在生成预览图时，第 N+1 批正在下载、正在被扫描），画成「阶段 2/3」等于用更好看的 UI 讲一个不准确的过程；且 v1 主进度条的右侧分母（「已入库 1,284 / 3,201」）没有数据来源，icloudpd 不报总数。三行并列才如实表达「三件事同时在跑」。同步行同理不画进度条，只给 `downloaded` 计数（这个字段后端一直在更新，此前前端从未展示）。「现在能看多少」放进扫描行原本写「待开始」的那一格，不新增元素。顶栏摘要与浮层大标题的落库文案收成 `landingSentence()` 一处，避免「正在下载新照片」多处硬编码 |
| 2026-11-03 | 删库的 `fsp.rm` 加 `maxRetries: 3` / `retryDelay: 200` | Node 的 `fs.rm` 默认 **`maxRetries: 0`**，Windows 上遇到 EPERM 一次就抛，用户只看到「删除库目录失败」而不知道重试一下就好。最现实的占用者是收尾中的缩略图任务：删激活库只做队列换代（`clearThumbnailQueue` 仅 `queueGeneration++`），已经跑起来的 ≤8 个任务不中断，sharp 关句柄的毫秒级窗口可能正好撞上 `rm`。3 次线性退避最坏多等 1.2 秒；若占用一直不释放（真有别的程序锁着）仍会失败并保留「记录保留可重试」出口。该选项只在 `recursive: true` 时生效 |
| 2026-11-03 | 缩略图/封面 URL 加 `lib=<库id>` 库作用域，后端不一致直接 404；删除 `AssetDto.thumbUrl` 死字段 | 资产 id 是**库内自增**，`/api/thumb/:id` 只按 id 查当前库。浏览器按 URL 分桶缓存，两个库在同一个 id 撞上同一个 `rev` 就会拿库 A 的图显示库 B 的照片——**这不是理论风险**：同批数据导入多个库时 mtime 被 `preserveTimestamps` 原样保留、扫描顺序又一致，id 与 rev 成片相同。`lib` 由 tasks store 在每份 `/api/stats` 落地时写入 `api/client.ts` 的模块变量（不散到 8 个调用点）。**两个关键设计**：① `lib` 缺省时不校验——前端拿到第一份 stats 之前不知道库 id，那段窗口必须能出图，宁可退回共享缓存也不能让整面墙 404；② `applyLibrarySwitch(activeId)` 必须在**重建视图之前**同步 `setThumbLibrary`——视图一重建就开始请求缩略图，等 `tasks.refresh` 回来再更新会让这批请求带旧库 id → 后端 404 → 图裂。顺带删掉后端响应里的 `thumbUrl: /api/thumb/<id>`：死字段（前端一律现拼）且不带 size/rev/lib，谁用了谁就绕过整套缓存键。判定抽成纯函数 `libMismatch(lib, currentLibraryId)` 以便单测（4 例） |
| 2026-11-03 | 设置页「当前库」**置顶 + 三层高亮**；切库从 `location.reload()` 改为**就地重建** | 当前库原先只在标题行挂一个小「当前」胶囊，边框与底色和其他库一模一样，库一多就得逐张找。现行做法是**描边 + 底色 + 置顶**三件事：`border-color` 蓝 + `box-shadow: 0 0 0 1px` 同心环（把 1px 边框视觉加厚到 2px，完全跟随 `border-radius`）+ 从左淡出的极淡蓝底；置顶解决另一半——高亮只管「看到之后好不好认」，不管「还得先滚到它」，而 `switchTo` 成功的卡片跳到顶部正好当「切成功了」的反馈。**否决「左侧 3px 蓝竖条」**：absolute 条宽仅 3px，声明的水平圆角 10px 会被 CSS 按「相邻半径之和超过边长则等比缩小」压成 <2px 近乎直角，与卡片 11px 圆角错位（左上/左下冒方角）；且条在 border 内侧，左侧 = 1px 边框 + 3px 条 = 4px、其余三边 1px，四边粗细不匀，整圈描边看起来是歪的。切库后原 `location.reload()` 会把设置页一起关掉（切完被弹回照片墙），改为四步重建：① 详情页 `/photo/:id` 的 id 属于旧库 → 先回照片墙；② 清 assets / search / selection 三个全局 store；③ KeepAlive 换 `key` 重建视图树（替换组件内部状态：搜索词、滚动位置、日期面板）；④ 重拉库列表与 `stats`。第 ③ 步选 **KeepAlive 加 key** 而不是给 `<component>` 加 key：后者会把旧 GridView 实例留在缓存里，反复切库累积 N 份已加载数据 |

**明确不做的功能**（已决策，不必再提）：HEVC 按需转码缓存、逆地理编码、收藏、最近删除、下载原片、内存 LRU、iCloud 云端删除类操作（`--auto-delete` / `--keep-icloud-recent-days` 一律不开放）。P2+-3 语义搜索（人脸/场景）暂缓。

## 四、踩坑台账

这些是「下次一定会再踩」的，写细一点。

- **`server/package.json` 的 `test` 脚本是显式文件列表，不是 glob**：新增测试文件必须手动加进去，否则 `npm test` **静默不跑它**，用例总数不涨，极易误判「已覆盖」。
- **判断审查做完了要逐项回代码验证**，不能按「有几批修复记录」推定。10-27 那轮六批 8+6+3+6+1+2 = 26 ≠ 30，缺的 4 项一度被写成「全部落地」。
- **PowerShell 引号**：`\"` 不是转义（用反引号），双引号内 `$` 会展开。复杂 JS/SQL 落临时 `.cjs` 文件再跑；多行 commit 用 heredoc（Git Bash）或 `Out-File` + `git commit --file=`。
- **sharp 0.33.5**：构造选项 `rotate:true` 不生效，必须链式 `.rotate()`。
- **虚拟滚动三坑**：① `estimateSize` 不在测量 memo 的响应式依赖里，尺寸变化必须显式 `measure()` 且**锚定首可视行**，否则视口跳几十行；② `GridItem :key="asset.id"` 不含 `rev`，组件会复用不重建，随 rev 变化的东西必须 getter 现读；③ 切数据源时 `props` 更新晚于同步调用，滚动归零必须 `nextTick` 之后调。
- **`fs.cp({preserveTimestamps})` 的 mtime 精度**：源 mtime 的 100ns 精度会被进位成 1ms（`...4331.9983` → `...332`），`Math.trunc` 取整后恰好差 1ms。判重必须留 1ms 容差，否则同一文件被判成两份。
- **`getDb()` 返回永不失效的 Proxy**：`await` 之后写 DB 会落到切库后的新库。跨 await 的操作要重新取库上下文。
- **全局单例状态不绑定库**：`scanProgress` / `syncState` / `importState` / `authState` 都是模块级单例，组件按库渲染却读全局状态 —— 这是当前 4 个 P0 的共同根因。任何「按库展示」的新功能都要先问：这个状态属于哪个库？
- **缩略图缓存写盘用原子写**：`.tmp` + `rename`，否则并发读会读到半截文件。
- **临时目录删除**：本机 `rm` / `fs.rmSync` 走系统回收站（安全钩子拦），仓库内临时文件用 `mv` 移出；`os.tmpdir()` 下的测试临时目录不受影响。
- **git commit message 用 heredoc**（`git commit -F - <<'EOF'`），Git Bash 下中文编码正常。
- **`git merge --no-ff <branch> -F -` 不认 stdin**，得先写临时文件。
- **git SSH 固定路径**：`core.sshCommand = "C:/Windows/System32/OpenSSH/ssh.exe" -o StrictHostKeyChecking=accept-new`，日常 `git push origin main` 畅通。注意本机有两套 git（系统 + WorkBuddy 自带 PortableGit），HOME 相同、共用全局配置。
- **缩略图缓存的 rev 是动态的**：前端 URL 带 `rev = 资产 file_mtime`（后端 `AssetDto.rev` / `dates.thumbRev` 下发），源文件一变 URL 就变、浏览器强制重拉，**不需要手动 bump 版本号**。`THUMB_REV` 常量只作无 rev 场景的兜底。
- **服务进程由用户自启**（后端 8899 / 前端 5173），不要占用；临时验证起进程用完就 `TaskStop`。
- **临时脚本放 `server/scripts/.*`**（dot 开头，已 gitignore 防误提交），用完即删。
- **删库/切库不需要「先切到别的库再删」**：崩溃与资源类竞态已清零，直接删是安全的。
- **「状态写库」不能挂在「前端轮询」上**：`auth_status` 曾经写在 `GET /api/auth` 里，用户提前关面板就永久丢结果。凡是「某个进程/任务已经产生的事实」，一律在该进程结束的位置落库，轮询只读不写（最多做兜底）。
- **`account` 有值 ≠ 已认证**：`POST /api/auth` 提交邮箱时就写了 `account`，验证码还没过。判断能不能同步只能看 `auth_status`，别图省事查 `account`。
- **判断状态是否可信要多看一层磁盘**：`auth_status='authed'` 也可能因为手工清缓存而不成立，读路径用之前先确认 cookie 文件真的在（`cookieExists`）。
- **长任务的进度入口不能只放在可关闭的弹窗里**：导入弹窗一关，后端流水线照跑却什么都不显示，用户会认为任务已停（2026-11-03 实测）。这类任务（导入、同步）的进度与取消必须落在顶栏/状态浮层这类常驻位置，弹窗只是详情视图；顺带要在弹窗里写明「关闭不会中断」。
- **chokidar 的 `ignored` 对目录也会调用**：想按扩展名过滤事件会把 `icloud/`、`import/` 这类无扩展名目录整个忽略掉，目录内事件全部丢失。过滤只能按「名字特征」（`.part`、`.db-wal`、`thumbs` 等），扩展名过滤留给 walkDir。
- **`awaitWriteFinish` 的代价是「每个待确认文件每 100ms 轮询一次，连查 2s」**：下载节奏稀疏时无所谓，本地导入每秒落几百个文件就是每秒上万次 stat + 同等数量定时器。这也是导入期间必须 `stopWatcher()` 而不靠 watcher 边导边扫的真正原因（不是笼统的「事件风暴」）。
- **缩略图入队不能前移到「入库瞬间」**：`doRunScan` 开头 `resetThumbnailProgress()` 把 status 置 `idle` 并 `batchId++`，此时 `enqueueAsset` 不把 batchId 记进任务、`recordThumbnailResult` 直接 return —— 任务照跑、缓存照写，但账本一动不动（进度条失真）。中途调 `beginThumbnailBatch()` 也不行：它按全表 COUNT 算 total，而此刻只有一部分行插入，total 会偏小。入队就留在每轮扫描末尾，靠「让扫描跑起来」提高出图频率。
- **导入的周期扫描不能改 `importState.phase`**：`phase === 'scanning'` 在前端（隐藏进度条/取消按钮）和 `requestImportCancel()`（直接拒绝）里都是「不可取消」的语义。归置期间必须始终保持 `copying`，否则用户想取消都点不动。
- **周期扫描用 fire-and-forget，不要 await**：`await runScan()` 会让归置在每个触发点停顿一整轮全库扫描（2 万库 1~2 秒 × 几十次），导入总时长明显变长。扫描互斥已由 `scanChain` 保证，只需一个单飞标记防止把请求堆进链里；丢掉一轮也无妨，结尾还有一次最终全量扫描兜底。
