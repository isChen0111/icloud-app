## 二、结论摘要

| 级别 | 数量 | 性质 |
|---|---|---|
| P0 | 4 | 会产生脏数据 / 双任务并发 / 不可逆误操作 |
| P1 | 16 | 功能错误、资源泄漏、状态永久卡死 |
| P2 | 18 | 健壮性、契约漂移、可维护性 |
| 文档 | 10 项 | 过期、互相矛盾、缺失 |

**一句话**：功能主流程的设计是对的（导入按日期归置 → 落库 → 补 EXIF 这条链没有结构性问题），**问题高度集中在「全局单例状态 × 多库切换 × 长任务」这三者的交错处**。近三轮功能迭代引入了导入、补写、双入口引导，但「任务归属哪个库」这件事始终靠一个全局变量表达，于是切换库时几乎每一类后台任务都有自己的漏法。

第二个共性问题是**注释与实现相反**（6 处），而且都出现在关键不变量上——这比缺少注释更危险，因为它会让后续维护（包括我自己）基于错误前提改代码。

## 三、P0（4 项，均已复核）

### C-01 导入的「取消」是假终态，会跑出两条流水线（最危险）

**证据**
- `import/index.ts:19-24`：`cancelImport()` 把 `importState.status` 直接改成 `'cancelled'`，这就是全部的取消信号
- `import/state.ts:45-47`：`isImportBusy()` 只判 `status === 'running'` → 取消后立刻返回 false
- `import/fsImport.ts:37-39`：`isCancelled()` 读的就是同一个 `status`
- `import/index.ts:62-63`：新任务 `resetImportState()` 后把 status 改回 `'running'`

**触发**：点「取消导入」→ 关闭弹窗 → 再次点「开始导入」。旧流水线此刻很可能正卡在 `fs.promises.cp()`（大视频几分钟）。

**后果**
1. 旧循环下一次 `isCancelled()` 返回 `false`，**继续拷贝**——取消等于没取消
2. 两条流水线同时向同一目录 `cp`，`pickTargetName` 的 exists 检查与实际写入互相不可见 → 同名覆盖或各自生成 `(n)`
3. 旧流水线结束时把 `status` 写成 `done`、`finishedAt` 覆盖新任务 → 前端立刻判定完成，`isImportBusy` 又变 false，可以再启第三个
4. 旧流水线的 `startWatcher()` 会在**新导入进行中**把 watcher 拉起来，正是「导入期间必须停 watcher」要避免的场景

**修法**：每次导入分配 `runToken`（或独立的 `cancelRequested` 布尔），`cancelImport` 只置信号，终态只由持有该 token 的流水线写回；`isImportBusy()` 覆盖 `running` 与过渡态 `cancelling`。

### C-02 切库后，仍在运行的缩略图任务把状态写进新库的同 id 资产

**证据**
- `pipeline/thumbnails.ts:173`：`const db = getDb()` 在 `await` 之前取
- `db/index.ts:173-181`：`getDb()` 返回**永不失效的 Proxy**，每次 `.prepare()` 都解析到「当前激活库」
- `pipeline/thumbnails.ts:243`：`UPDATE assets SET thumb_status='done' ...` 在 `await extractVideoFrame(...) / sharp(...)` **之后**执行
- 同类问题在 `:364`（`ensureSize` 宽高回填）

**触发**：缩略图/大图生成或宽高回填正在跑（几百 ms ~ 60 s），用户切库。`libraryBusyGuard` 只挡扫描/同步/导入，**不挡缩略图队列**。

**后果**
- 新库中恰好同 id 的资产被标记 `thumb_status='done'`（实际没有缓存文件）或 `'error'` + 旧库的错误文案
- 若用户此时点「忽略」，该资产在新库 `thumb_ignored=1`，`ensureThumbnail` 永远返回 null → **这张照片永久没有缩略图**
- `ensureSize` 把旧库照片的宽高写进新库资产 → 网格宽高比错、详情尺寸错

**修法**：任务开始时快照 `config.dbPath`，执行写库前比对，不一致直接放弃（不改任何行）。

### C-03 统计体积缓存跨库串台，并把旧库数值以新库名义落盘

**证据**：`routes/stats.ts:72`（模块级 `totalBytesCache`）、`:109`（`walkSize(config.libraryRoot)` 结果写入）、`:115`（落盘 JSON 里的 `libraryRoot` 是写入那一刻的库）

**触发**：`walkSize` 遍历数万文件（数秒~数十秒）期间切库。

**后果**：新库首屏显示旧库的 GB 数，并写进新库的 `stats.json`；失效条件只比 `assetCount` 与 `scanRunId`（`:147-151`），两库资产数恰好相同时就会一直沿用错值。反向还会用新库路径去 `rmSync` 旧库的 `stats.json`。

**修法**：四个变量改成以 `config.dbPath` 为 key 的 Map，或切库时显式 reset 并作废在算任务。

### C-04 同步子进程退出事件没有归属校验，可以出现两个 icloudpd 同时写同一库

**证据**：`icloudpd/sync.ts:141` → `handleSyncExit()` `:153-154` **第一行就 `proc = null`**，全程没有 `proc !== child` 判断。
对照 `icloudpd/auth.ts:266` 已经做了这件事（R-09 修复时补的），同步侧漏了。

**触发**：取消同步后立刻再点同步。`taskkill` 是同步返回的，但 libuv 的 `exit` 事件可能在新请求之后才到。

**后果**
1. 新进程失去引用 → `cancelSync()` 再也杀不掉它
2. 新任务状态被旧事件改写成 `error`
3. 用户看到 error 再点一次 → **两个 icloudpd 同时跑、同时写同一库目录**（正是代码注释里最担心的场景）

**修法**：事件回调首行 `if (proc !== child) return`，`proc = null` 移进判断内。

## 四、P1（16 项）

### 导入链路

**C-05 `runScan` 无互斥，取消后仍跑全库扫描（已复核）**
`scanner/index.ts:167` 的 `runScan` 只做 `scanProgress.runId++; status='scanning'`，没有重入保护；`routes/stats.ts:221` 的 `POST /api/scan` 不看 `isImportBusy()`；`import/index.ts:47` 的末扫描也不看。两次扫描各持一份遍历快照，先开始的那次在 `collectOrphanIds`（`:565`）里把后来导入的文件判成孤儿 → 删 DB 行 + FTS + 缩略图。另外取消导入后 `runScan` 照跑（`ImportStatus` 没有「扫描中」阶段），期间 `libraryBusyGuard` 以「扫描中」拦住切库，用户以为结束了却什么都不能做。

**C-06 `status='done'` 早于落库扫描（已复核）**
`fsImport.ts:196` 设 `done` → 前端 `pollImport` 立刻 `stopPolling` + 刷新统计，但此刻库里一行都还没入库（`runScan` 在 `import/index.ts:47`，要几十秒）。用户看到「导入完成」而照片墙空白，必须手动刷新。修法：终态推迟到 `runScan` 之后，或在状态里加 `scanning` 子阶段。

**C-07 move 跨盘用 `copyFile` 丢 mtime（已复核）**
`fsImport.ts:52-63`：同盘 `rename` 没问题，EXDEV 分支 `copyFile` + `unlink` —— `copyFile` **不保留 mtime**（与 `fs.cp({preserveTimestamps})` 不同）。后果：无 EXIF 的 HEIC/PNG/视频在扫描时拿到的日期变成「今天」，判重键同步失效。修法：EXDEV 分支改 `fs.cp(..., {preserveTimestamps:true})` + unlink。

**C-08 `mkdirSync` 在 per-file `try` 之外（已复核）**
`fsImport.ts:165` 位于资产循环体顶部、`try`（`:169`）之前。目标盘满 / 目录被占用 → 抛到 `runImportPipeline` 的 catch → `status='error'`，**剩下所有资产都不再处理**，且不进失败清单。修法：移进 try，失败时对 `parts` 逐个 `recordFailure` 后 continue。

**C-09 `fs.cp` 非原子，中断会在正式文件名上留半写文件（未复核，按 Node 语义推断）**
`fsImport.ts:175` 直接写目标路径。写一半失败/取消/断电 → `import/YYYY/MM/DD/正式名` 上留截断文件，紧接着的 `runScan` 会把它当正常资产入库（照片墙上出现永远打不开的图），下次导入时 mtime 不匹配还会多生成 `(n)`。修法：写 `*.part` 再同目录 rename。

**C-10 上传文件名未过滤 Windows 保留名与非法字符（已复核）**
`import/upload.ts:24-36` 只拦绝对路径与 `..`。`filename` 完全由客户端决定，`preservePath:true` 直接透传。`CON.jpg` / `NUL.jpg` / `aux.jpg` → `open` 成功但字节流向设备，**文件不落盘且接口返回 200「导入完成」**；`a:b.jpg` 在 NTFS 上变成备用数据流；`x.jpg.` 与 `x.jpg` 会被 Win32 归一化成同一个文件，后传的静默覆盖前一个。修法：段名黑名单 + `[\\/:*?"<>|]` + 结尾点/空格 + 长度上限，非法则改名而非整批失败。

**C-11 上传时单个文件失败中断整批，已写入的 GB 数据被删掉（已复核）**
`routes/import.ts:101-123` 的 `try` 包住整个 `for await`。5000 张里 1 个文件非法/超限 → 跳出 → `cleanImportTempDir` 删掉临时目录 → 用户从头再传，错误信息还是英文 errno。修法：per-part try/catch 记失败项继续，最后统一返回 `{ok, failures}`。

**C-12 上传期间切库 → 文件落旧库、扫描扫新库（已复核）**
`routes/import.ts:84` 只在请求开始时 `resolveActiveLib`，上传可能持续几十分钟；`startUploadImport`（`import/index.ts:81-103`）不重校验。此刻 `importState` 还是 idle，`libraryBusyGuard` 放行切库。后果：文件按旧库落盘，末尾 `runScan` 扫的是新库根 → 旧库一个都不入库，接口却返回 `ok:true`、状态跑完 `done`。修法：`start*Import` 内重校验 `getCurrentLibrary()?.id === lib.id`，不一致 409 并清临时目录。

**C-13 补写降级静默 + mtime 还原失败被当成普通失败（已复核）**
- `fsImport.ts:129`：exiftool 不可用时 `return`，**两个计数都是 0** → 900 多张一张没补，界面显示「导入完成」，事后无法区分「本来就有 EXIF」与「降级跳过」
- `metadata/exifWrite.ts:92-95`：`utimesSync` 失败会抛到 `patchExif` 的 catch → 只记 `exifFailed++`。但此时文件已落位、mtime 已是补写时刻 → **判重键被破坏**，再导一次会多出 `(1)` 副本，而用户只看到「补写失败 1 个」

### 认证与进程

**C-14 认证定时器只在成功分支清理；`code=0` 但无 cookie 时永久转圈（已复核）**
`icloudpd/auth.ts:259-284`：`clearTimeout(authTimer)` 只在 `code===0 && cookieExists()` 分支里。① 密码错误 → 10 分钟后 `onAuthTimeout()` 把准确原因无条件改写成「认证超时」，排错方向被带偏；② `code===0` 但没有 cookie → 两个分支都不进，`stopPolling()` 已执行、进程已退出，`session.stage` 永远停在 `waiting_code`。

**C-16 没有优雅关闭与进程级兜底（已复核）**

## 六、代码质量评估

### 6.1 健壮性

**做得好的地方**：单任务互斥（sync/import）都有 409；缩略图原子写 + `isCacheUsable`；删除对账的三重白名单（遍历不完整 / stat 失败 / SCAN_LIMIT）；队列世代令牌替代 `p-queue.clear()`；`runProcess` 的双 settle 保护与超时后等 close；`guard.ts` 先 `realpathSync` 再比较。

**系统性弱点**：**「任务归属哪个库」没有一等公民**。`scanProgress` / `syncState` / `importState` / `authState` 四个全局单例，只有 `importState.libraryId` 一个字段，且只在启动时写入、之后从不校验。C-02/03/04/15 都是这一个根因的不同表现。建议引入统一的「操作上下文」（`{ libraryId, dbPath, startedAt }`），所有异步任务在关键写回点校验上下文是否仍然有效。

### 6.2 注释

**优点**：关键决策都有「为什么」而不是「做什么」——`conflict.ts:9-18` 解释为何不比 size、`exifWrite.ts:9-20` 解释为何用 exiftool 而非 sharp、`queue.ts` 解释为何弃用 `p-queue.clear()`。这类注释质量高于多数项目，是真正的资产。

**问题：6 处注释与实现相反，且都在不变量上**

| 位置 | 注释说 | 实际 |
|---|---|---|
| `db/libraries.ts:35` | 库名会用作 cache/cookie 目录名 | 目录是 `lib<id>`，库名只是别名（同文件 `:7-8` 描述正确，自相矛盾） |
| `pipeline/queue.ts:150-152` | 切库后旧 id 查不到即跳过，无害 | `db` 是 Proxy，写的是新库的同 id 行 |
| `App.vue:284` | 保持 `librariesChecked=false`，下次再查 | `finally` 无条件置 true，且无人读取 |
| `fsImport.ts:7-10` | 移动会保留 mtime | EXDEV 分支 `copyFile` 不保留 |
| `import/index.ts:5` | 与 icloud 同步零耦合 | 反向不互斥：同步可以在导入中途启动 |
| `config.ts:99` | `>0` 时同步命令追加 `--recent` | 全项目无引用，`.env.example` 明写「代码不再读取」 |

这六处建议**与代码修复同批改掉**，因为它们是「下次改错」的直接诱因。

### 6.3 优雅度

- **重复模式没有抽象**：四个 state 各写一遍 `reset / public / shape`；前端两套轮询、两套同步状态行
- **单函数过长**：`scanner/index.ts` 677 行里，`runScan` 一个函数占 `167-640`（473 行），承担遍历、日期解析、配对、UPSERT、对账、缩略图入队、缓存清理、进度上报 8 件事。它已经是测试覆盖最好的部分（`scan.test.ts` 走真实链路），拆分风险可控，收益是可读性
- **正面对照**：`import/` 目录是本次迭代里模块化做得最好的部分——`types / state / index / fsImport / upload / pair / conflict / resolveDate / guard` 各自单一职责，`guard.ts` 是纯函数、`conflict.ts` 是纯函数，因此都能被单测直接钉住

### 6.4 耦合度

- **无循环依赖**：`import → scanner` 单向，`routes/* → import/scanner` 单向，依赖图是干净的层次结构
- **但有一个隐式耦合源**：`db/index.ts` 的「永不失效 Proxy」让切库零改动，代价是**任何持有 `db` 引用的异步任务都会在 await 之后自动指向新库**（C-02）。这是一个「用便利换正确性」的典型 trade-off
- **前端与后端没有共享类型**：`web/src/types.ts` 手写一份 DTO，已经漂移出 3 处（P2-17）。短期可在 `types.ts` 顶部标注「必须与 `server/src/routes/*.ts` 的返回结构同步」，中期抽 `shared/` 包
- **常量重复**：`IMAGE_EXTS` / `VIDEO_EXTS` 在 `scanner/index.ts:25-26` 与 `import/fsImport.ts:23-24` 各一份（当前内容相同）。新增扩展名时必然漂移，后果是「导入了但不入库」，且不报错

### 6.5 模块化小结

| 维度 | 评价 |
|---|---|
| 后端分层（routes / pipeline / scanner / import / metadata / db / utils） | 清晰，职责边界可读 |
| 后端超大文件 | `scanner/index.ts` 需拆；其余 < 500 行 |
| 前端组件粒度 | `App.vue` 1565 行、`SettingsView.vue` 1342 行偏大，但都是「页面壳 + 弹窗编排」，暂不建议为了行数而拆；真正该抽的是「同步状态行 + 轮询」这一对重复 |
| 测试与模块的对应 | 单测基本一比一落在纯函数和独立模块上，这是模块化良好的直接证据 |
