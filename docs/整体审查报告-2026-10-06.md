- 审查方式：静态代码审查、文档与实现交叉核对、当前前端构建和后端类型检查、隔离的队列行为复现。未修改业务代码，也未对用户源照片库做写入或删除操作。

## 一、结论摘要

项目的主干设计基本适合个人本地照片库：源文件、数据库和可重建缩略图缓存有清楚的边界；全量骨架与分页缓存能够支撑万级资产；搜索和照片墙复用数据源接口；扫描、媒体处理与 API 也已有一定分层。

本次没有发现足以判定“当前数据已被错误批量删除”或“照片内容被上传”的证据。但有 **2 项高优先级并发/加载问题**，其中并发预算超限已通过隔离实验复现；另外有 **5 项中优先级可靠性、安全边界或可维护性风险**。最需要关注的是：

1. 后台与交互预览图队列并未严格共享一个并发闸门，配置上限为 8 时可同时运行 9 个任务。
2. 虚拟列表卸载图片组件只释放了浏览器调度器的本地槽位，没有取消或撤销已经进入服务端交互队列的工作；快速滚动可能让已离屏任务继续占用处理能力。
3. 文件监听会响应同路径文件变化，但扫描会无条件复用旧元数据，且没有让已完成的缩略图缓存失效。

建议优先修复前两项，再补齐文件变更识别和关键路径自动化测试。当前代码**不建议进行大范围重写**；应先用测试固定并发、扫描、删除、分页等行为，再逐步拆分中心编排模块。

### F-01 — 并发上限不是严格的全局上限

**证据：**[queue.ts](../server/src/pipeline/queue.ts#L23-L35) 分别根据另一个队列的 `pending` 设置两套 `PQueue.concurrency`；交互任务在 [queue.ts](../server/src/pipeline/queue.ts#L147-L153) 直接加入交互队列。任务进入队列时会立即启动，而并发值变更通过队列事件排到微任务中处理。

**复现：**使用与生产逻辑相同的两个 `PQueue` 和并发调整公式，先阻塞 8 个后台任务，再加入 1 个交互任务。观测结果为 `backgroundActive=8`、`interactiveActive=1`、`running=9`，超过配置的 8。原因是 `Math.max(1, ...)` 会在另一个队列已经占满预算时仍为当前队列保留至少一个执行位；暂停队列也不会终止已经运行的后台任务。

**影响：**违反“所有缩略图任务总运行数不超过 8”的策略保证。通常是短时超限，但后台任务已在运行时，用户交互会额外叠加资源消耗；极端并发加入时，两个独立队列的调度状态也难以审计。

**建议：**改用单一全局 semaphore/调度器计数正在运行的任务，并在一个公共调度点决定下一项工作。交互优先应体现在“下一项选择顺序”，而非两个队列各自推导并发值。增加可重复测试，断言任何任务完成/入队时 `running <= 8`，并覆盖 8 个后台任务运行中突然加入交互工作的场景。

### F-02 — 快速滚动卸载图片后，服务端工作仍可能继续

**证据：**[gridThumbnailScheduler.ts](../web/src/composables/gridThumbnailScheduler.ts#L88-L105) 在组件取消时会从前端 `active` Map 移除任务并释放本地槽位；[useLazyImage.ts](../web/src/composables/useLazyImage.ts#L53-L59) 在组件卸载时调用该取消函数。但缩略图 API 在 [thumb.ts](../server/src/routes/thumb.ts#L34-L52) 会把请求放入服务端交互队列并等待生成，当前路径没有把客户端断开信号传递给队列任务，也没有在排队前判断请求是否已失效。

**影响：**快速拖动时，虚拟列表销毁离屏 `<img>` 后，浏览器侧可能发出取消，但已经进入服务端队列的任务仍可继续排队或生成。前端槽位释放后会为新视口继续派发请求，因而浏览器限制的“最多 8 个在途请求”并不能约束服务端积累的陈旧工作。服务端处理能力可能被中途视口占用，造成拖回已访问区域时也要等待。审查期间的浏览器资源记录出现过约 **4.5–11.2 秒**的缩略图首字节等待；这与排队风险一致，但目前 API 没有交互队列独立指标，无法仅凭该记录确认每个延迟请求的具体排队来源。

**建议：**

- 给排队工作保存请求/资产/优先级信息；请求尚未开始时，客户端断开应能撤销或跳过该工作。
- 对共享同一缩略图的请求继续做 in-flight 合并；有其他有效等待者时，不应因某个客户端断开就取消共享生成。
- 让最终视口任务优先于仍未开始的旧视口工作，并分别暴露“运行中交互任务数、等待交互任务数、被取消数”。
- 端到端测试快速跨越多个未生成区后回到缓存区，验证队列长度不会随滚动次数持续增长。

### F-03 — watcher 检测到文件变化，但同路径覆盖不会刷新资产

**证据：**[watcher.ts](../server/src/scanner/watcher.ts#L63-L66) 监听 `change` 并触发扫描；扫描在 [scanner/index.ts](../server/src/scanner/index.ts#L158-L178) 按相对路径读取现有元数据，在 [scanner/index.ts](../server/src/scanner/index.ts#L273-L303) 命中已有路径时直接复用它们。虽然 UPSERT 会写入日期、尺寸等字段，但这些值就是从旧 DB 取出的；流程没有比较 mtime、文件大小或 checksum。[thumbnails.ts](../server/src/pipeline/thumbnails.ts#L72-L84) 发现缩略图缓存文件存在时直接返回，也没有源文件版本校验。

**影响：**如果同一路径上的照片/视频被覆盖或被同步工具修订，watcher 会触发一次看似成功的同步，但 DB 元数据和已生成的 WebP 缓存可能仍是旧内容。路径删除后重新添加则是另一条路径语义，不应与覆盖更新混为一谈。

**建议：**扫描时维护源文件签名（至少 `size + mtimeMs`，需要更强正确性时再用 checksum）。签名变化后重新提取元数据、将相关缩略图状态设为待生成并删除/版本化缓存。若产品明确只支持“路径不可变的只读快照”，则应缩小 watcher 的 `change` 承诺并在用户文档明确说明。

### F-04 — CORS hook 没有拒绝普通的非允许 Origin 请求

**证据：**[index.ts](../server/src/index.ts#L42-L59) 只在允许来源时设置 CORS 响应头；只有 `OPTIONS` 请求会对不允许来源返回 403。带其他 `Origin` 的普通请求不会被 hook 拒绝，而会继续进入路由；例如 [stats.ts](../server/src/routes/stats.ts#L182-L196) 中会触发扫描的 POST。

**影响：**CORS 响应头限制的是浏览器脚本读取响应，不等同于服务器拒绝请求或 CSRF 防护。服务只绑定 `127.0.0.1`（[index.ts](../server/src/index.ts#L89)），降低了远程网络暴露面，但不能据此认定来自其他网页/本机上下文的副作用请求一定不会抵达；具体浏览器的 localhost/Private Network Access 策略会影响可利用性，因此此项按安全加固风险报告，不宣称已验证可跨浏览器利用。

**建议：**对有副作用的路由实施明确的来源/Fetch Metadata 校验，并设计本地 CSRF token 或一次性配对机制；保留开发环境明确允许的 Vite 来源。不要只依赖“没有 `Access-Control-Allow-Origin`”来阻止操作。

### F-05 — 搜索查询失败会被显示成没有搜索结果

**证据：**[search.ts](../server/src/routes/search.ts#L139-L146) 捕获数据库/FTS 异常后只记录 warning，随后 [search.ts](../server/src/routes/search.ts#L146) 仍以正常 JSON 返回 `total=0`、空月份与空结果。[GridView.vue](../web/src/views/GridView.vue#L128-L136) 会将总数为 0 的状态显示为“没有找到匹配”。另一方面，[search.ts](../server/src/routes/search.ts#L142-L143) 的日志意味着服务端虽有记录，但用户 UI 无法区分真正无命中与查询失败。

**影响：**索引损坏、FTS 语法/资源异常或 SQL 问题会产生“假无结果”，用户可能误以为照片不存在。前端网络错误也会把页写入 `failed` 集合，但该集合未作为错误状态显示，容易产生同样的体验。

**建议：**对真正无匹配返回 200 空结果；对数据库/FTS 异常返回 5xx 和可识别错误码，前端展示“搜索失败，可重试”，不要伪装成零结果。对用户输入本身不支持的短词或非法词，仍可返回正常的明确提示。

### F-06 — FTS 索引每次启动都会被主动清空重建

**证据：**[schema.ts](../server/src/db/schema.ts#L73-L80) 的 `SCHEMA_SQL` 每次执行都会 `DROP TABLE IF EXISTS assets_fts` 再创建。随后 [db/index.ts](../server/src/db/index.ts#L36-L53) 通过行数不一致检查回填。由于新建 FTS 表必然为空，正常已有资产的每次启动都会触发全量回填。

**影响：**当前万级库可能尚可接受，但“行数一致性修复”实际上无法避免启动重建；资产规模增长后，启动时同步执行的 FTS 写入会增加启动延迟，并使 schema 变化与数据恢复耦合。行数相等也不能发现“FTS 内容错误但条数相同”的损坏。

**建议：**将 FTS 表纳入版本化迁移，不在常规启动路径上无条件删除；使用事务内维护或明确的索引版本/校验状态，仅在 schema 变化或确实不一致时重建。重建耗时应有日志与启动阶段指标。

### F-07 — FFmpeg/FFprobe 子进程没有超时

**证据：**[ffmpeg.ts](../server/src/ffmpeg.ts#L85-L111) 使用 `spawn`，只监听 `error` 和 `close`，没有 deadline、AbortSignal、kill 或超时后的进程清理。

**影响：**遇到损坏媒体、FFmpeg 卡住或外部进程异常时，对应 promise 不会完成，调用方占用的队列槽位会一直不释放。多个此类任务可能持续降低后台和交互缩略图吞吐；服务关闭时也缺少统一的子进程回收策略。

**建议：**按操作类型（缩略图抽帧、HEIC 解码、ffprobe）配置超时时间；超时后终止子进程并等待 `close`，记录资产 ID、操作类型和 stderr 尾部。测试超时与进程启动失败路径。

## 三、架构与产品层面评估

### 做得较好的部分

- **数据流适配度较好：**照片墙和搜索实现相同 `GridDataSource` 形态，减少了两套虚拟列表的重复实现。
- **本地优先边界明确：**默认 loopback 监听、缓存可重建、源媒体与派生缩略图区分；删除前也有确认。
- **容量意识到位：**万级列表使用虚拟滚动与分段分页；统计目录体积时主动让出事件循环；缩略图采用请求生成与后台补齐组合。
- **恢复机制已有基础：**分页/详情/search 的部分异步操作有版本序号保护，扫描不完整时会跳过删除对账。

### 耦合与臃肿风险

- `GridScroller.vue` 集中维护虚拟行计算、日期导航、滚动位置恢复、图片调度器生命周期和数据源初始化；这是照片墙核心的合理聚合，但已成为高回归风险文件。建议逐步抽出纯行模型函数、滚动/缩略图调度 composable，并保留组件负责模板组合。
- `queue.ts` 同时负责双队列并发策略、浏览活动租约、缩略图进度快照和任务结果聚合。F-01 说明并发规则已经不适合继续通过多个可变 `PQueue.concurrency` 间接表达；建议拆成一个有不变量测试的调度器与独立的进度服务。
- `App.vue` 同时承载全局主题、统计轮询、浏览活动通知、失败项管理和弹层状态。后续功能继续增加前，可将资源状态面板/轮询封装成独立模块；无需为此立即重写全局状态。
- 总体判断为**局部编排集中、尚未到需要整体重构的程度**。优先补边界测试和明确不变量，再做渐进式拆分。

### 产品与文档一致性

- 删除是永久删除源文件；当前确认流程降低了误操作概率，但产品仍依赖用户自行备份。建议确认文案始终明确“从磁盘永久删除”，并清楚呈现部分文件 unlink 失败后的实际状态。
- 搜索最短 3 字符是 trigram 的实现限制，README 已说明；界面应继续明确告知，不应让短关键词像无结果一样静默结束。
- 文档中的资产数量仍是 **12,591**（例如 [架构设计文档.html](./架构设计文档.html#L60) 与 [上下文快照](./CONTEXT-项目上下文快照.md#L6)）；审查时运行中的 `/api/stats` 显示 **12,609**。架构文档仍标为 2026-09-21 生成，性能数字 `0.68s/25ms` 也应标成历史样本，而非当前保证。建议把“实测快照日期”与“当前运行数据”分开记录，避免固定数据看起来像实时状态。
