# 导入功能审查与重构方案

日期：2026-11-01
范围：`server/src/import/*`、`server/src/routes/import.ts`、`server/src/metadata/*`、`web/src/components/ImportDialog.vue`
触发：导入功能反复出现「重复导入多出副本」「日期对不上」「判重失效」等意外问题

---

## 一、结论

现在的问题不是某一处写错，而是**身份模型选错了**：导入用一个**不稳定的东西**（文件 mtime）当作「这是不是同一个文件」的判据。

mtime 有三个天生缺陷：

1. **会漂移**：复制、跨盘移动、云同步、exiftool 写盘都可能改变（实测已出现 1ms 进位，见 §2.1）
2. **不是内容**：两个不同文件可以有相同 mtime，同一文件在不同机器上 mtime 不同
3. **无记忆**：每次导入都重新猜，猜错的代价是用户库里多一份副本

补 EXIF 让这个缺陷从「偶发」变成「必然」：补写改内容、不改 mtime，于是「同名不同内容」与「同一文件」在判据上无法区分。

**方向**：把身份改成「源文件身份账本 + 内容哈希兜底」两级判重，让判重不再依赖目标文件的时间戳；同时补上目前完全缺失的目录安全守卫。

## 二、问题清单

### P0-1 源目录与库目录无任何重叠校验（危险）

`routes/import.ts:56-67` 只做了 `stat` 判断「是不是目录」，没有判断源目录与库目录的关系。

| 用户误操作 | 后果 |
|---|---|
| 源目录选成库根 `iCloudPhoto/lib1` | `icloud/` 与 `import/` 全部再导一遍（同一批照片在库内出现两份） |
| 源目录选成项目根 `F:\iPhone\icloud-app` | 把 `server/cache`、`web/dist`、`node_modules` 全遍历一遍（慢，但不会导入） |
| 源目录选成盘符根 `F:\` | 扫描整盘，可能触发数小时的任务 |

现有代码零防护，且导入是后台任务，用户点完就走，发现问题时已经写入大量文件。

### P0-2 判重依赖 mtime，跨实现传递必漂移

实测（2026-11-01，`lib6/import/2020/01/02/有日期照片.jpg`）：

```
源文件 mtimeMs = 1793504594331.9983   （带亚毫秒尾数）
复制后目标     = 1793504594332        （Windows 保留时间戳时按 100ns 进位）
Math.trunc 后  331 vs 332 → 判为「不同文件」→ 生成 (1) 副本
```

已用 1ms 容差临时堵住（`conflict.ts: MTIME_TOLERANCE_MS`），但这是**堵漏不是修根**：容差 1ms 能挡舍入，挡不住「用户把库拷到另一块盘再拷回来」「云盘同步改 mtime」「资源管理器改文件属性」。

**本质问题**：拿目标文件的属性，去证明「源文件已经导入过」。这两件事没有必然联系。

### P0-3 没有持久化的导入记忆

每次导入都是「从零开始猜」：

- 无法回答「这张照片是哪次导入的」
- 取消后不知道哪些文件已经落位（`importState` 只是内存计数器）
- 换一个源路径重导同一批照片，全部重新猜一遍
- 判重失效时没有任何可回溯的记录

`assets` 表里的 `checksum` 列（`schema.ts:60`）从建库起就预留，但**从未写入过**（全项目仅此一处引用）。

### P1-1 同名不同内容 → 无上限副本

`pickTargetName` 的第三步是「换个名字继续试」。如果判重失效（如 P0-2），每重导一次就多一份 `(1)`、`(2)`、`(3)`…… 用户看到的是照片墙里同一张照片出现 N 次，且没有任何提示说明为什么。

### P1-2 二级判据只有 size + mtime，补写 EXIF 后 size 必变

补写会改变文件字节数（实测 274 → 3445、1477915 → 1480908），所以 size 判据在补写场景下永久失效，只能去掉（已按方案 1 去掉）。去掉之后，判重只剩 mtime 一根独木。

### P1-3 补写范围偏窄

实测 **HEIC 同样可以写 EXIF 且 mtime 能保住**（`IMG_7935.HEIC` 1477915 → 1480908 字节，`DateTimeOriginal` 写入成功）。当前 `isPatchableImage` 只认 `.jpg/.jpeg`，库里 94 个无日期 HEIC 永远补不上。

### P1-4 上传链路「先全量落盘，再开始导入」

`routes/import.ts:92-106` 把整个上传写完才调 `startUploadImport`。

- 需要 `cache_dir` 有等同上传总量的空余空间（几十 GB 上传 = 几十 GB 临时文件）
- 中途断网 → 整个会话临时目录删除，已传部分全部白费
- 非媒体文件也照传照写，最后被 `collectSourceFiles` 过滤掉，白占带宽和磁盘

### P2 其它

| 问题 | 位置 | 影响 |
|---|---|---|
| 同基名多图时「主资产」由 `walkDir` 顺序决定 | `pair.ts:59` | 实况配对的主资产可能不是用户预期那张，日期取自主资产 → 可能落错目录 |
| 0 字节文件进入流水线 | `collectSourceFiles` | 后续 EXIF/sharp 全部失败，记入失败清单，污染统计 |
| 源目录遍历用 `statSync` 同步循环 | `fsImport.ts:81` | 5 万文件级目录会阻塞事件循环（已有每 200 个让出，仍偏保守） |
| `importState` 纯内存 | `state.ts` | 服务重启后无法查询历史导入 |

## 三、目标设计

### 3.1 身份模型：源文件身份账本（import_ledger）

**核心变化**：判重的依据从「目标文件的属性」改成「源文件的身份 + 一次导入留下的记录」。

```sql
CREATE TABLE IF NOT EXISTS import_ledger (
  -- 源文件身份：来源前缀 + 归一化相对路径（小写、正斜杠）
  --   local:<relPath>   本机迁移
  --   upload:<relPath>  上传（浏览器 webkitRelativePath）
  source_key   TEXT PRIMARY KEY,
  -- 落位结果（相对库根，如 import/2015/05/03/a.jpg）
  target_path  TEXT NOT NULL,
  -- 源文件签名（用于判断源文件是否被替换过）
  size         INTEGER NOT NULL,
  mtime_ms     INTEGER NOT NULL,
  -- 是否补写过 EXIF（补写过的源 size 与目标 size 必然不同，记录以便解释）
  patched      INTEGER NOT NULL DEFAULT 0,
  -- 批次号，取消/回溯用
  batch_id     TEXT NOT NULL,
  imported_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_ledger_target ON import_ledger(target_path);
```

存放位置：**library.db**（每库一份，删库即删账本，天然不串库）。

**为什么用「源相对路径」而不是内容哈希做主键**：

- 零成本：不用读文件内容，`stat` 就能算
- 完全免疫 mtime 漂移：比的是**源**的 mtime（我们刚读到的），不是目标文件的
- 重复导入同一目录时命中率接近 100%（这是最高频的场景）

**为什么还需要内容哈希**：换电脑、换目录名、从 U 盘拷过来导入，`source_key` 全变了 → 账本 miss。这时靠二级判重（§3.2）。

### 3.2 三级判重

```
第 1 级：ImportLedger（源身份）
  source_key 命中 && size 相同 && |源 mtime - 记录 mtime| ≤ 1ms
    → 校验 target_path 文件仍存在（不存在则删掉这行，继续往下判）
    → 存在：skipped（记 skipByLedger）
    → 不存在：视为「用户删过这张」，重新导入并更新账本

第 2 级：同名文件 + 内容哈希（历史数据 / 换了源路径）
  目标目录已有同名文件：
    size 相同 && |mtime 差| ≤ 1ms        → skipped（现有逻辑，保留）
    否则 → 计算源与目标内容的 sha256
      相同 → skipped（记 skipByHash），并补写账本
      不同 → 另存 (n)（记 renamed）

第 3 级：新文件
  直接落位，写账本
```

**哈希只在第 2 级冲突时计算**，所以：

- 首次导入（账本空、目标为空）→ 零哈希，零额外 IO
- 重复导入同一目录 → 第 1 级命中，零哈希
- 换路径重导 → 第 2 级全量哈希，一次性成本（3.4MB 文件约 21ms，见实测）

### 3.3 目录安全守卫（必须）

在 `routes/import.ts` 的 `POST /import/scan` 里、`startLocalImport` 之前加：

```ts
/**
 * 导入源目录合法性检查。返回错误文案，null = 放行。
 * 核心：源目录不得与库目录（library_root）互相包含，也不得是盘符根。
 */
function validateSourceDir(sourceDir: string, libraryRoot: string): string | null
```

规则（全部先 `path.resolve` + 小写归一）：

| 情形 | 处理 |
|---|---|
| 源 == 库根 | 拒绝：「不能把照片库自身当导入源」 |
| 源是库根的子目录 | 拒绝：同上（会导入 icloud/ 或 import/ 自身） |
| 库根是源的子目录 | 拒绝：「所选目录包含照片库，会把库内文件再导一遍」 |
| 源 == 盘符根（`F:\`、`C:\`） | 拒绝：「不能选择整个磁盘」 |
| 源目录不可读 / 是文件 | 拒绝（现有逻辑保留） |

### 3.4 补写范围扩展到 HEIC

`isPatchableImage` 改为 `.jpg/.jpeg/.heic/.heif`。依据：实测 HEIC 写入成功、mtime 保留、EXIF 段被正确替换。PNG/GIF 不做（EXIF 非其标准结构），视频不做（`creation_time` 需 remux）。

### 3.5 进度与可观测

`ImportProgress` 增加分类计数，替代现在含糊的 `skipped`：

```
skippedByLedger   账本命中（上次导过）
skippedByHash     内容相同（换了路径/历史数据）
renamed           同名不同内容，已另存 (n)
patched           补写了拍摄时间
failed            失败
```

前端完成文案从「已处理 3/3 · 跳过 2」变成「新增 1 · 已导入过 2 · 补写时间 1」。

### 3.6 批次

每次导入生成 `batchId`（时间戳+随机串，与上传会话 id 同规格），写进账本。用于：

- 取消后查询「这次已经落了哪些」
- 未来「撤销本次导入」（删文件 + 删账本行）

## 四、兼容与迁移

| 存量状态 | 处理 |
|---|---|
| 老库无 `import_ledger` | 建表幂等执行；账本空 → 全部走第 2 级判重 |
| 第 2 级命中且判为 skipped | **自愈**：顺手补写一行账本，下次就走到第 1 级 |
| 已存在 `(1)` 副本的历史脏数据 | 不自动清理；提供只读清单（`GET /api/libraries/:id/import/duplicates`）供人工确认 |
| `assets.checksum` 预留列 | 保持不写；哈希只在判重瞬间算，不入库（入库会引入「何时失效」的新问题） |

## 五、测试计划

现有 112 例全部保留。新增用例（每条都要做变异验证）：

| 用例 | 断言 | 变异验证方式 |
|---|---|---|
| 同目录导入两次（第二次源文件 mtime 被改） | 第二次全 `skippedByLedger`，无新副本 | 去掉账本查询 → 应变红 |
| 账本命中但目标文件被删除 | 重新导入，账本行被更新 | 去掉 `existsSync` 校验 → 应重复导入（红） |
| 源路径改变后重导同一批（同名同内容） | `skippedByHash`，不产生 (1) | 去掉哈希分支 → 应生成 (1)（红） |
| 同名但内容不同 | `renamed`，生成 (1) | — |
| 源目录 = 库根 / 库根子目录 / 盘符根 | 400 + 明确文案 | 去掉守卫 → 应放行（红） |
| HEIC 无 EXIF → 导入 | 补写成功，`patched=1` | 把扩展名白名单改回只 JPEG → 应 skipped 补写（红） |
| 取消导入后再导入同一目录 | 已落位的走 `skippedByLedger`，未落位的继续 | — |

## 六、分期建议

### 第一期（P0，半天，建议立刻做）

1. 目录安全守卫（§3.3）—— 防灾难，改动小、收益最大
2. `import_ledger` 建表 + 第 1 级判重 + 命中校验 target 存在
3. 第 2 级保留现状（size+mtime 容差），命中时自愈写账本
4. 进度分类计数 + 前端文案

做完之后：**重复导入同一个目录 = 零成本全跳过，且不再受 mtime 漂移影响**。

### 第二期（P1，一天）

5. 第 2 级冲突时算内容哈希（根治换路径重导的重复）
6. 补写扩展到 HEIC
7. 批次号 + 取消后可查

### 第三期（P2，可选）

8. 上传分批（每批 200 个文件 / 2GB，独立会话）
9. 服务端上传扩展名白名单前置过滤
10. 存量 `backfill-exif` 命令 + 重复文件清单接口

## 七、一句话总结

现在是把「时间戳」当身份证用，而时间戳是最容易被人改的东西；改成「自己记账 + 偶尔对指纹」，判重才真正稳。
