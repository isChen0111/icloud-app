## 一、结论摘要

10-06 报告列出的 F-01～F-07 已全部落地，本次回归**未见复发**：全局限流已是单一调度器（8 并发不变量有测试守住）、FTS 不再每次启动重建、FFmpeg 已有超时回收、搜索异常已返回 5xx、源文件签名（`size + mtimeMs`）已生效。

但 10-18 之后新增的「多库管理 + 客户端删除 + 引导流程」三块功能带来了新的高优先级问题，共 **3 项 P1、20 项 P2、7 项 P3**，其中三项 P1 都可小改大收益：

1. **删除照片后照片墙出现永久空洞**（前端）。`removeAssets` 把受影响页 `filter` 短了 `k` 条，却不丢弃该页，页起点仍按 `PAGE` 整数倍对齐 → 该页尾部 `k` 个全局位置没有任何页持有，只有整页刷新才恢复。
2. **删除激活库存在竞态，Windows 上大概率 500**（后端）。`closeDb()` 后 `await fsp.rm(cache_dir)` 期间 `config.dbPath` 仍指向被删库，前端 5 秒一次的 `/api/stats` 轮询会经 `ensureOpen()` 重新建库 → 删正在被打开的文件 → EPERM。
3. **扫描删除对账有两个漏洞会误删仍在磁盘上的资产记录**。`statSync` 失败直接 `continue` 而不记入 `traversal.errors`；`walkDir` 对符号链接/联接点目录既不递归也不记错。两者都会让「遍历不完整就不对账」的保护失效。

P2 里有三条同源（队列身份的跨库污染）：`inFlight` 去重键不含库 id、`inFlight` 不随切库清空、`p-queue.clear()` 让排队 Promise 永不 settle。建议合并为一个分支统一处理。

## 三、P1 逐条详述

### R-01 — 删除照片后照片墙出现永久空洞

**证据：** [assets.ts:220-232](../web/src/stores/assets.ts#L220-L232)：找到包含被删资产的最小页起点 `minPage`，`filter` 掉被删 id 后 **`pages.set(minPage, next)`**（页长变成 `PAGE-k`），只 `delete` 掉 `minPage` 之后的页。而 `getRange`（[assets.ts:63-73](../web/src/stores/assets.ts#L63-L73)）按 `p = floor(start/PAGE)*PAGE` 步进 `PAGE` 取页，隐含假设「每页恰好 `PAGE` 条」。收尾的 `for (const p of retryPages) ensureRange(p, p + PAGE)` 只重拉**原先有在途请求**的页，`minPage` 若不在其中就不会被重拉。[GridView.vue:80-81](../web/src/views/GridView.vue#L80-L81) 删除成功后只调 `assetStore.removeAssets(ids)`，没有 `refresh()`。

**触发条件：** 在照片墙内删除任意 1 个以上资产（单张或批量），然后继续滚动 / 不刷新页面。

**影响：** 全局位置流已整体前移 `k` 位，但 `minPage` 页仍从 `minPage` 开始装——页尾 `minPage+PAGE-k .. minPage+PAGE-1` 这 `k` 个位置没有任何页持有。`getRange` 返回长度 `PAGE-k` 的数组，对应网格最后 `k` 格永远渲染为空；后续页虽然重新拉取且内容正确，但**这 `k` 个位置在 UI 上就是空洞**，直到整页刷新（`refresh()` 重建全部页）才消失。用户感知为「删了几张，墙上莫名少了几格且点不开」。

**建议：** 删除后直接 `pages.delete(minPage)`（丢弃该页让它整页重拉，代价是一次 `PAGE` 条请求），或维护「页内缺口」元数据并在 `getRange` 里做补偿。前者一行改动即可，且能顺带消掉「页长不齐」这个全局隐患——长期看应把「每页必满 `PAGE`，末页除外」写成不变量并用测试守住。

### R-02 — 删除激活库存在竞态，Windows 上大概率 500

**证据：** [libraries.ts:191-207](../server/src/routes/libraries.ts#L191-L207)：`isActive` 分支先 `stopWatcher()` → `clearThumbnailQueue()` → **`closeDb()`**（195 行），随后 `await fsp.rm(lib.cache_dir, ...)`（201 行）。整个过程中 `config.dbPath` / `config.cacheDir` **仍指向被删库**——`applyLibraryPaths(next)` 在 214 行，位于删除成功之后。此间任何经 `getDb()` 的调用都会走 Proxy → `ensureOpen()`（[db/index.ts:31-46](../server/src/db/index.ts#L31-L46)）：`fs.mkdirSync(dirname)` 重建目录 + `new Database(config.dbPath)` 新建一个空 `library.db`。前端 `App.vue:333` 是 5 秒一次的 `stats` 轮询，删除大库（缩略图数十 GB）时 `fsp.rm` 往往要跑几秒，撞上概率不低。

**触发条件：** 删除当前激活库且 `removePhotos` 为真或缓存目录较大；删除期间前端仍有轮询/缩略图/详情请求。

**影响：** 三件事叠加：① 轮询刚重建的 `library.db` 被 `fsp.rm` 撞上 → Windows 上 `rm` 对被占用文件报 `EPERM`，接口 500 且 `deleteLibrary(id)`（207 行）与后续 `applyLibraryPaths` **都没执行**；结果是库仍注册、缓存被删掉大半、`countAssets` 变 0，前端处于「库还在但空了」的坏状态。② 即使 `rm` 成功，目录被重建的现象会让「删除」看起来没删干净。③ 若最后切到 `resetLibraryPaths()`，还会留下一个孤立的 `cache/lib<id>/library.db`。

**建议：** 删除前先把上下文切走：`isActive` 时立刻 `applyLibraryPaths(next)` 或 `resetLibraryPaths()`（让 `config.dbPath` 指向新位置或默认位置），再删文件；并在删库期间加一个「库操作中」熔断标志，使 `ensureOpen()` 在窗口内不重建（或让 `getDb()` 抛可识别的 503）。同时给 `deleteLibrary` 与 `applyLibraryPaths` 加 `finally` 兜底，避免 EPERM 后注册表与文件系统不一致。

### R-03 — 扫描删除对账的两个漏洞会误删仍在磁盘的资产

**证据：** 对账本身有保护（[scanner:423](../server/src/scanner/index.ts#L423)：仅 `scanLimit <= 0 && traversalComplete` 才删），但 `traversalComplete` 只统计 `walkDir` 收集的 `errors`，而有两类「看不见的文件」不会进 `errors`：

1. **`statSync` 失败静默跳过**：[scanner:129-135](../server/src/scanner/index.ts#L129-L135) `try { statSync } catch { continue }` —— 该文件既没进 `allFiles`，也没写 `traversal.errors`，因此 `traversalComplete` 仍为 `true`，而它对应的旧 DB 行在 `dbRows` 里 → 被判孤儿 → `deleteAssetById`（删行 + FTS + 缩略图缓存）。讽刺的是 [scanner:414-415](../server/src/scanner/index.ts#L414-L415) 的注释明确写着「stat 瞬时失败的文件在 walkDir 阶段会被跳过，不会因 IO 抖动误删」——注释与实现相反。
2. **符号链接 / Windows 联接点目录**：[scanner:74-84](../server/src/scanner/index.ts#L74-L84) 只处理 `entry.isDirectory()` 与 `entry.isFile()`。符号链接（`isSymbolicLink()`）在 `withFileTypes` 下两者皆为 `false`，于是既不递归也不记 `errors`。若照片库根下存在联接点（把照片目录挂在别的盘），其下全部资产 100% 被判孤儿。而 chokidar 默认 `followSymlinks: true`，会「监听得到、扫描看不见」——正好是最容易产生「莫名少照片」的组合。

**触发条件：** ① 扫描时某文件被杀软/同步工具短暂锁定（Windows 常见）；② 照片库目录树中存在联接点或符号链接目录。

**影响：** DB 行、FTS 索引、缩略图缓存被一并删除。下次扫描文件重新可读时以**新 id** 复活（`AUTOINCREMENT`），于是用户在该资产上的「忽略预览图失败」「已删除到客户端」等状态全部丢失，详情深链 hash 失效。

**建议：** ① `stat` 失败时把 `relPath` 加入白名单集合并令 `traversalComplete = false`（宁可跳过整轮对账，也不要误删）；② `walkDir` 显式分支 `entry.isSymbolicLink()`——跟随（`statSync` 判类型）或记 `errors`，二选一但必须显式；③ 修正 414-415 行注释与实现一致。

## 四、P2 逐条详述

### R-04 — 源文件签名变化只重置缩略图，元数据仍复用旧值

**证据：** [scanner:306-326](../server/src/scanner/index.ts#L306-L326)。命中 `existingMeta` 时计算 `changed`，`changedRelPaths.add(...)` 后仍把 `exist.dateTaken / exist.width / exist.height / exist.duration / exist.orientation / exist.gpsLat / exist.gpsLon` 原样写回 UPSERT。F-03 只让缩略图重生成（402-409 行删缓存），没有重新提取元数据。

**触发/影响：** 覆盖同一路径的视频（时长/分辨率变了）或照片（EXIF 拍摄时间变了）后，缩略图会更新，但 `date_taken` 与宽高比永久陈旧 → 排序位置错、网格宽高比错（`GridScroller` 用宽高比决定某些布局）、详情面板信息错。这与 F-03 想兑现的「同路径覆盖自动失效」承诺只兑现了一半。

**建议：** `changed` 分支改为重新提取元数据（图片走 EXIF、视频走 ffprobe）后再写 UPSERT；提取失败时回退旧值并记日志。成本只在「确实变化的文件」上发生，不影响常规扫描。

### R-05 — 后台任务链式 `throw` 未被捕获，Node 22 默认退出进程

**证据：** [queue.ts:135-146](../server/src/pipeline/queue.ts#L135-L146)：`job` 内部 `.catch((error) => { recordThumbnailResult(false); throw error })`，然后 `void scheduler.submit(job, ...)` —— `void` 丢弃了 Promise，`:146` 的 `throw` 成为**未处理拒绝**。Node 22 默认 `--unhandled-rejections=throw`，会直接终止进程（服务整体挂掉，前端所有请求断）。

**触发条件：** `ensureThumbnail` 抛出的非业务异常，例如 `generate`（[thumbnails.ts:104-116](../server/src/pipeline/thumbnails.ts#L104-L116)）里的 `getDb().prepare(...)` 在库被删/切库瞬间失败——注意这段 DB 读取在 `try {` **之前**，不受 `generate` 内部错误处理保护；又如切库瞬间 `path.join(config.libraryRoot, ...)` 组合出不可读路径后 `existsSync`/`sharp` 抛错。

**影响：** 后台补图跑着跑着服务消失，日志里只有一条 unhandled rejection。属于「低频但致命」。

**建议：** `.catch` 内记录失败后**不再 rethrow**（批账已记失败，无需向上传播）；或 `void scheduler.submit(...).catch(logAndSwallow)`。同时把 `generate` 的 DB 查询纳入 `try`，让「库不存在」变成 `return null` 而非异常。

### R-06 — `clear()` 让排队任务 Promise 永不 settle

**证据：** [queue.ts:179-183](../server/src/pipeline/queue.ts#L179-L183) `clearThumbnailQueue()` → `scheduler.clear()`；`p-queue` 的 `clear()` 实现是 `this.#queue = new Queue()`（已核对 `node_modules/p-queue/dist/index.js`），被丢弃任务的 `deferred.resolve` 永不调用。`runInteractiveThumbnail`（[queue.ts:109-116](../server/src/pipeline/queue.ts#L109-L116)）的调用方是 `routes/thumb.ts` 的请求处理，它 `await` 这个 Promise。

**触发/影响：** 切库/删库瞬间，所有排在队里的 `/api/thumb` 请求挂死——不回响应、不报错，HTTP 连接与前端调度器槽位一起泄漏（前端 8 个槽位被占满后整墙不再加载新图，直到刷新）。删库时尤其容易命中（`clearThumbnailQueue` 正是删库第一步）。

**建议：** 队列层提供「丢弃并结账」的语义：`clear()` 前把待执行任务逐个 reject（带 `QueueCleared` 标记），路由层捕获该标记后返回 503/`Retry-After` 而不是 500；或让路由对 wait 加超时，超时返回 503。

### R-07 — `inFlight` 键不含库 id 且不随切库清空

**证据：** [thumbnails.ts:66](../server/src/pipeline/thumbnails.ts#L66) `key = ${assetId}:${size}`（不含库标识），[thumbnails.ts:85-90](../server/src/pipeline/thumbnails.ts#L85-L90) 命中即复用；`clearThumbnailQueue` 只清 `scheduler` 与 `queued`，**不清 `inFlight`**。

**触发/影响：** 每个库的资产 id 都从 1 连续编号，切库后新库 id=5 的请求会复用旧库 id=5 的在途 Promise → 拿到的可能是旧库已删文件的路径，或 `null`（旧库行已删）。表现为新库部分图「一进来就空白且保持空白」，直到该 Promise 完成后再请求才恢复。窗口短但确实存在。

**建议：** `inFlight` 键加库 id（如 `${libraryId}:${assetId}:${size}`，libraryId 从 `getCurrentLibrary()` 取），并在 `clearThumbnailQueue` 中一并清空（丢弃在途 Promise 引用不影响其继续跑完，只是不再被复用）。

### R-08 — `date_taken` 混存 UTC `Z` 与 `+08:00` 两种表示

**证据：** [metadata/index.ts:199-209](../server/src/metadata/index.ts#L199-L209) `normalizeDate`：`Date` 实例走 `toISOString()` → `...Z`（UTC）；字符串形式的 EXIF `"2025:02:17 18:55:12"` 补成 `...+08:00`（本地）。而**目录日期兜底** [metadata/index.ts:24](../server/src/metadata/index.ts#L24) 是 `T00:00:00+08:00`。实测：用库内真实 HEIC 调 `exifr.parse(..., { pick: ['DateTimeOriginal'] })` 返回的是 `Date`（`toISOString()` 得 UTC）→ 有 EXIF 的照片与视频都是 `Z`；无 EXIF 的走目录兜底 → `+08:00`。只读抽查 `library.db` 确认库中确实存在 `T00:00:00+08:00` 的 photo 行。

**影响：** `assets` 按 `date_taken` TEXT 排序。`+08:00` 的 `2025-02-17T00:00:00` 在字符串序里落在 `2025-02-16T16:00:00Z` 之前 8 小时的位置——真实时刻是 16:00Z。于是这批资产在时间线上前移 8 小时，跨日/跨月时月份分组计数与实际不符（月初/月末的资产跑到相邻月份），`/api/dates` 的月份头位置与照片实际月份对不上。

**建议：** 统一成单一基准。最省事的是**全部存本地无偏移**（`YYYY-MM-DDTHH:mm:ss`，`normalizeDate` 的 `Date` 分支改为按 `Asia/Shanghai` 格式化），读取端不再做时区推断；或全部存 UTC 并让目录兜底也 `-08:00` 折算。改完需要一次性迁移已有行（可用 `date_taken` 是否含 `Z` 判定来源，但两种表示无法完全反推，建议在迁移时只修正 `+08:00` 那批为 UTC 等价形式）。

**建议（三选一，都不需要动「切库 = 刷新」这个前提）：**

- **C（最小兜底）**：不改后端，只在引导第 3 步检测非激活时把「开始全量拉取」换成「切换到此库并拉取」，设置中心对非激活库把 `SyncButton` 替换成「切换到此库」。

无论选哪个，都应给 `SyncButton` 增加明确的「非激活库」禁用态 + 文案，避免用户把它当成真 bug。

### R-30 — 主界面 `syncError` 只赋值不渲染，切库被拒时静默失败

**证据：** [App.vue:39](../web/src/App.vue#L39) 声明 `const syncError = ref('')`，在 `pickLibrary`（:69）、`runSync`（:228）、`cancelSyncRun`（:241）三处 catch 里写入；但全文搜索 `App.vue` 只有这 6 处引用，**均位于 `<script setup>` 内，模板里从未渲染它**（对比 `SettingsView.vue` 有 `.sync-note.err` 行、`OnboardingView.vue:200` 有 `onboard-error` 行，主界面这条链路缺了展示端）。

**触发条件：** 同步任务执行中（`isSyncBusy()` 为真），在顶栏库下拉点另一个库 → `PATCH /api/libraries/:id/active` 被 [libraryBusyGuard](../server/src/routes/libraries.ts#L83-L97) 拦下返回 409「同步任务执行中，请先等待完成或取消后再切换照片库」。

**影响：** `pickLibrary` 第一行就把 `libMenuOpen = false` 关掉了菜单，catch 写进一个没人看的 ref，库名保持不变——用户观感是「点了一下，什么都没发生」，既不知道被拒绝，也不知道原因（需要先取消或等完成）。会反复点击、甚至怀疑服务卡死。同一个缺陷还吃掉了顶栏「执行同步」被 409（已有任务在执行）和「取消同步」失败的全部提示。

**建议：** 把后端返回的 `message` 原样渲染出来（后端文案已经区分了「同步中」「扫描中」「其他库执行中」三种原因，无需前端另造）：顶栏状态条加一行 `.sync-note.err`，或统一切一个轻量 toast 组件。这一条与 R-22 同为「409 有正确文案但用户看不到/看不到关键原因」的同一类问题，建议同批处理。
