iCloudPD 照片库拉取同步 · 架构功能设计文档

项目：iCloud 本地照片浏览器（Vue3 + Node.js/Fastify + SQLite + sharp）· 状态：设计稿（未实施）· 2026-10-09 · 版本 v0.1

1. 背景与目标

当前照片库由用户手动使用 icloudpd 官方 exe（GitHub Release 分发）在命令行完成：登录 iCloud、全量拉取、增量更新。整个过程脱离应用，无法在网页端操作。

本次目标

  • 网页端一体化：在应用内完成「创建照片库 → 链接 iCloud（账号/密码/验证码）→ 全量拉取 → 日常增量同步」闭环，不再需要手敲命令行。
  • 多照片库支持：一个应用实例管理多个照片库（不同 iCloud 账号 / 不同目录），网页端可切换浏览。
  • 健壮性：cookie 过期可感知并引导重新链接；下载中断可重新执行续传；关键操作有明确状态反馈。

2. icloudpd 调研结论（2026-10-09，v1.32.3）

官方仓库：github.com/icloud-photos-downloader/icloud_photos_downloader（MIT，约每周五发版，支持 Windows/Linux/macOS；可用 exe / Docker / PyPI / npm 安装）。
维护风险提示：官方 README 顶部标注「Looking for MAINTAINER」——项目在寻找新维护者。版本演进速度与维护质量存在不确定性，集成时应把 icloudpd 作为独立进程黑盒调用，避免深度耦合（见 §3.1）。

2.4 认证与 cookie 机制（官方文档要点）

  • MFA 有效期：Apple 设置，当前约 2 个月过期，过期后必须重新认证；Apple 要求所有新账号开启 MFA。
  • 会话检查：官方推荐用 --auth-only 验证会话是否仍有效（认证失败即视为过期）。
  • 过期通知：icloudpd 支持 SMTP 邮件/脚本通知（--smtp-*、--notification-script）——本项目不采用，改为应用内状态提示（见 §3.3）。
  • 常见认证错误：可清理 --cookie-directory 内容后重试。
  • 多账号/多配置：一条命令内 --username 多次，其后参数作用于该账号；cookie 目录可共用（按用户名分文件）——下载侧原生支持多库。

3. 技术方案设计

3.1 后端集成架构：以「进程黑盒」方式驱动 icloudpd

沿用现有 runProcess 模式（server/src/ffmpeg.ts）的经验：后端 spawn icloudpd exe，参数走数组（不经 shell，无注入面），子进程输出经管道回传，配合超时 kill 防卡死。核心原则：

  • 黑盒调用：不把 icloudpd 源码/逻辑并入项目，只解析它的 stdout/退出码判断结果——降低官方项目维护波动的影响。
  • 可执行文件定位：配置 ICLOUDPD_EXE（默认 server/vendor/icloudpd-1.32.3-windows-amd64.exe），与 ffmpeg 同一套路径解析策略；自动安装：postinstall 串联 scripts/install-icloudpd.ps1，从仓库 Release vendor-binaries 下载（已存在跳过，ICLOUDPD_URL 可覆盖源）。
  • 任务模型：每次下载/认证 = 一个后台任务（见 §5 数据模型），有状态、进度、日志、可重试。

3.1.1 认证流程设计（网页端输入邮箱/密码/验证码）— 已实现（webui 桥接）

最终方案（2026-10-12 实现落地）：自绘认证面板 + icloudpd webui 桥接。console 管道方案实测不可行（icloudpd 的密码读取走 getpass 直读 Windows 控制台，不经过管道，管道化会挂起），已放弃。落地路径：后端 spawn icloudpd --password-provider webui --mfa-provider webui --auth-only（webui 监听 127.0.0.1:8080），前端自绘分步面板，输入经后端桥接写入 webui；完成判据 = 进程退出码 0 + cookie 落盘。

启动命令（--domain cn + webui provider + --auth-only，用户名必填）：

icloudpd --username <邮箱> --password-provider webui --mfa-provider webui \
         --cookie-directory <库cookie目录> --domain cn --auth-only

交互流：后端轮询 127.0.0.1:8080/status 解析当前阶段（等待密码 / 等待验证码）；前端分步面板按阶段显示输入框 → 前端 POST /api/auth/input → 后端转 POST 到 webui 的 /password / /code → 认证完成进程退出、cookie 落盘 → 状态 authed。

认证状态机（每库）： none（未链接）→ starting（进程启动中，前端只显示转圈、不暴露输入框）→ waiting_password（输密码）→ submitting（校验中，输入框/按钮全隐藏，只显示转圈文案）→ waiting_code（输验证码）→ done（成功，authed）/ error（失败，可重试）；同步遇 cookie 失效 → expired（前端显示「需要重新链接」）。

接口行为判定
POST /api/authspawn icloudpd webui auth-only（参数数组、日志脱敏）；启动轮询 webui 状态成功：进入 starting；失败：error + 错误信息
POST /api/auth/input接收密码或验证码，桥接写入 webui（/password | /code）；inputLock 防重锁——同一时刻只处理一次提交，防连点/并发造成重复发验证码请求写入成功 = 进入下一阶段（密码→submitting/waiting_code，验证码→submitting/done）
GET /api/auth前端轮询认证状态（阶段变化才解锁输入）阶段/错误变化即返回最新状态
POST /api/auth/cancel取消认证：taskkill /T 杀进程树 + 清理进程终止即取消

成功判定（关键）：进程退出码 0 且 cookie 目录生成会话文件 → authed。超时：认证任务 10 分钟无进展 → taskkill 进程树并置 error（可重试）。安全：密码/验证码仅驻留内存，经后端桥接写入 webui，不落日志、不进 DB；已链接库 固定邮箱不可改（换邮箱会造成照片库目录/会话错乱，需先删除照片库再新建）。

已知防重要点：2026-10-12 实测曾出现「输入密码后手机收到两次双重验证弹窗」——重复路径包括前端连点提交、轮询解锁时机过早、webui 内部重发 MFA。已上 inputLock + 前端 submitting 锁（提交后锁定，轮询到阶段变化/错误才解锁）收敛；若仍复现，优先检查后端日志「忽略重复提交」与 /code 被多次 POST。

3.1.2 cookie 保存与安全

  • 每库独立 --cookie-directory（server/cache/lib<id>/cookies，与缓存同库目录，见 §3.2.2 目录规则），互不干扰；cookie 文件含会话令牌，属敏感数据。
  • 密码与验证码只经自绘面板 → 后端桥接 → webui 通道传递，不进后端业务日志、不进 DB；后端对子进程命令行做脱敏（密码参数不落日志）。

3.1.3 cookie 过期检测与网页端应对

环节设计
主动检测每次下载任务前先跑 --auth-only 快速验证会话（成功≈几秒）；失败 → 会话过期
下载中过期icloudpd 下载失败且错误特征为认证失败 → 任务标记 auth_expired
前端应对库状态变为「需要重新链接」→ 照片库状态组件（§4.2）提示 → 点击重新进入认证流程（§3.1.1），不丢失已下载数据
定期巡检可选：启动时 + 每 N 小时对已链接库做一次 auth-only 巡检，提前发现过期

3.1.4 下载中断 / 网络中断 / 重新执行

  • 幂等续传：icloudpd 默认 Copy 模式「本地已存在跳过」——中断后重跑即从断点继续，无需特殊对账。
  • 任务可重试：下载任务失败（网络/超时）→ 状态 error + 可一键重试；后端限制并发（每库 1 个下载任务，避免重复 I/O）。
  • 断网恢复：与现有 5s 轮询一致——下载任务异常后前端看到错误态，网络恢复后点「增量同步」续跑。
  • 增量优化：增量同步命令追加 --until-found 20（默认值可配置），减少本地 I/O。

3.1.5 Apple 端索引间歇性 → 下载任务内置自动重试

实测现象（2026-10-09）：icloudpd 偶发报 Apple iCloud Photo Library has not finished indexing yet（validate 响应 webservices 为空），同一条命令短时间间隔内结果反复（12:54 成功 → 12:57 失败）；用户手动 bat 亦曾遇。此为 Apple 云端状态（照片服务未就绪），非本地/参数问题，等待即可恢复，重试是有效手段。
  • 错误识别：任务输出含 has not finished indexing 即命中（特征明确，可精确匹配）。
  • 重试策略：命中后等待 30~60 秒自动重试，默认最多 5 次；仍失败才标记 error，前端可手动再触发。
  • 设计要点：重试期间任务状态显示「等待 iCloud 索引完成…」，不占下载并发槽；重试次数与间隔做成可配置项（默认 60s × 5）。

3.2 多照片库架构（现有架构评估 + 改造方案）

产品决策（用户已定，2026-10-09）：多库采用 「单活跃库」模式——同一时间只有一个库被激活浏览/同步；切换库 = 停止当前库全部任务 → 关闭其 DB 连接 → 激活新库 → 前端整页初始化（不同库内容互不相干，不保留滚动位置/已加载状态）。后台任务为全局单一队列、任务带库标记：只执行当前活跃库任务，非活跃库任务挂起排队；未来可选扩展「空闲轮转」（活跃库无任务时处理其他库积压，纯调度策略，架构不动）。

3.2.1 现状评估（单库硬编码）

层现状多库障碍
config.ts单例：libraryRoot / cacheDir / dbPath（环境变量覆盖）只支持一个库
db/index.tsgetDb() 模块级单例只有一个 DB 连接
scanner / watcherrunScan、startWatcher 单例启动单库扫描/监听
routesassets/thumb/video/stats/search/info/thumbnail-errors 全部读全局 config + getDb路由无库维度
web storesassets/search/stats 无库维度切换库需整体刷新
结论：可行，但属于中等-大型重构（「全局单例」→「库注册表 + 库上下文」）。按用户产品决策收敛为单活跃库（见上文），比「多库并行上下文」成本低一档，且保留每库隔离与未来并行扩展点。

3.2.2 改造方案（单活跃库版）

  1. 库注册表：新增 libraries 表（应用级 meta.db，放 server/cache/meta.db，所有库共享），应用启动时加载全部库配置（路径/账号/cookie/参数）；只存元数据，不实例化。目录规则（已落地，库名只是别名，不参与路径）：照片根 = <项目根>/iCloudPhoto/lib<id>；缓存 = server/cache/lib<id>（library.db / thumbs / cookies 都在这）；注册表 = server/cache/meta.db（放 cache 根，不随库切换）。
  2. 库上下文（LibraryContext）+ 激活生命周期：每库一个运行时对象（独立 DB 连接、缓存目录、cookie 目录、扫描器/watcher、icloudpd 参数）。激活规则：同一时间仅一个库处于激活；切库 = 切换事务「停旧库任务 → 关旧库 DB/释放 cache → 开新库 DB/初始化 watcher → 通知前端整页刷新」；现有 getDb()/config 改为「当前激活库」上下文注入。新建库不自动激活：已有激活库时新建仅注册，主页面/下拉/设置中心保持原库（首次建库才激活）。
  3. 全局任务队列 + 库标记 + 路由绑定：缩略图/同步任务为全局单一队列，每条任务带 library_id；调度器只执行当前激活库的任务，非激活库任务保持「挂起」排队不执行。路由请求绑定当前激活库（请求级解析「当前库」），无需路径前缀大改。
  4. 前端：新增 libraries store（当前库 + 库列表）；切库 = 重置 assets/search/stats 全部状态 + 整页初始化（不保留滚动位置/已加载内容，用户决策）；照片墙状态按库独立。
  5. 下载侧：每库一条 icloudpd 命令（--username 指定该库账号 + --directory 指向该库目录 + --cookie-directory 该库 cookie），天然隔离。
  6. 扩展点（可选，P2+）：调度器加一条规则——当前激活库无任务时，从挂起队列取其他库任务执行（空闲轮转）；架构不变。

4. 产品功能设计

4.1 首次启动引导（无照片库状态）— 已实现

触发：后端启动后无任何已注册库（GET /api/libraries 返回空）→ 前端主页中央引导卡片。

主页中央引导卡：
  「创建你的照片库」
  ① 输入照片库名称（如：我的相册）→ 校验：非空、≤32 字符、库名唯一、不含路径非法字符
  ② 点击「创建照片库」→ POST /api/libraries（建库动画 + 成功提示；已有当前库时新建不切换，
     仅首次建库自动激活）→ 手动「下一步：链接 iCloud」（不自动跳转，由用户控制节奏）
  ③ 认证面板：自绘分步状态机（§3.1.1）——starting → 输密码 → 校验 → 输验证码 → 结果动画；
     每步 UI 独立：校验中只显示转圈文案（不残留输入框/标题），成功绿色 ✓ / 失败红色 ✗ 弹出动画，停留不自动消失
  ④ 认证成功（状态机 → authed）→ 手动「开始全量拉取」（不自动拉取：拉取有运行代价，由用户决定何时执行）
  ⑤ 点击 → POST /api/library/:id/sync {kind: full} → 进度显示（已下载/总数）
  ⑥ 完成 → 进入照片墙浏览

流程状态机：无库 → 创建中 → 认证中(starting→waiting_password→waiting_code) → 认证完成(authed) → 全量拉取中(running) → 就绪(idle)。中途失败（error）：可回退重试，已下载文件不丢失（Copy 幂等）。

字段与校验：库名（唯一、≤32 字符）、账号邮箱（来自 icloudpd 认证，设置中心完整展示）、目录（后端自动派生 iCloudPhoto/lib<id>，不开放手填）。异常分支：认证超时（10 分钟）→ 提示重试；Apple 端 has not finished indexing → 显示「等待 iCloud 索引完成」+ 自动重试（§3.1.5）；全量拉取中断 → 标记 error，可「增量同步」续传。

4.2 全量拉取 / 增量同步按钮（左上角同步状态组件）

位置：resource-status 下拉 popover-heading 内「照片库已同步」标题下方、原「共检查 N 个媒体文件。」说明文字行位置（去掉该行说明，改放同步按钮；不新增区域、不重构既有 UI）。

  • 单个按钮承载全部交互（全量/增量合并、执行/取消合并），四态动画切换：
  • ① 同步 ▾：默认态（云下载图标），点击展开小菜单（全量拉取 / 增量同步 二选一，菜单项带图标）；
  • ② 执行 · 全量拉取 / 执行 · 增量同步：选中态（主色实心 + 播放图标），点击即开始；
  • ③ ⟳ xx 执行中 · 点击取消：运行态（spinner 动画 + 行内进度条动画），再次点击即取消；
  • ④ 取消/完成后回到「同步 ▾」。按钮固定最小宽度与高度，状态切换不跳变。
  • 排队态仅作用于真正排队的库：其他库执行中时，未排队的库按钮保持「同步」可正常选择执行；只有选定后进入排队的库才显示「排队中」（时钟图标 + 悬浮提示），当前任务结束后自动启动。
  • 进度条为演示动画，真实实现接入拉取任务进度百分比。
  • 全量 = 整库重新校验 + 补下载（Copy 全量）；增量 = --until-found 20 快速增量——日常使用。
  • 每库同时只允许 1 个下载任务；认证过期时该区域显示「需要重新链接」入口（§3.1.3），点击打开认证面板并立即自动开始认证（已链接库固定邮箱，免二次点击）。
  • 全量拉取一律由用户手动触发（首次引导链接成功后也不自动拉取，见 §4.1）。
  • 全局状态同步：同步状态存于库级全局状态（一处启动，主界面与设置中心 §4.4 同一数据源实时一致，按钮文案/动画/取消能力同步）。

4.4 设置中心（右上角设置按钮）— 已实现

① 照片库管理

  • 每库一张卡片：库名 + 「当前」标识 + 链接状态胶囊（已链接 / 会话过期 / 未链接）+ 照片 N · 视频 M 计数（实时打开各库 DB 计算）+ 完整账号 + 目录 / 缓存 / 会话路径 + 最近同步独立一行
  • 链接入口：未链接库 → 「新建链接」（输邮箱）；已链接/过期库 → 「刷新链接」（固定邮箱不可改，点击打开认证面板立即自动开始认证，免二次点击）

  • 每库卡片提供同步操作：与主界面（§4.2）同款单按钮四态，且与主界面共享同一库级同步状态（一处启动，两处实时一致）
  • 一次仅一个库执行同步：其他库任务执行中时，本库点「执行」→ 后端 409 → 进入「等待执行…」态（disabled），全局任务释放后自动恢复；未执行任务的库按钮保持「同步」可正常选择执行

② 照片库配置（每库卡片内展开，与照片库绑定、默认全部锁死只读）

5. 数据模型与 API 设计

5.1 新增表（应用级 meta.db，位于 server/cache/meta.db）

libraries                                    -- 多库共享一份注册表
  id            INTEGER PRIMARY KEY AUTOINCREMENT
  name          TEXT UNIQUE NOT NULL         -- 库名（显示别名，不参与路径）
  library_root  TEXT NOT NULL                -- 照片根 = <项目根>/iCloudPhoto/lib<id>
  cache_dir     TEXT NOT NULL                -- 缓存 = server/cache/lib<id>（library.db/thumbs）
  cookie_dir    TEXT NOT NULL                -- 会话 = server/cache/lib<id>/cookies
  account       TEXT                         -- iCloud 账号邮箱（设置中心完整展示）
  auth_status   TEXT NOT NULL DEFAULT 'none' -- none / authed / expired
  last_sync_at  TEXT                         -- 最近同步时间
  created_at    TEXT NOT NULL
  active        INTEGER NOT NULL DEFAULT 0   -- 单活跃库标记（同一时间仅一个 = 1）

同步任务状态不入表（单任务模型）：全量/增量任务为全局单任务，状态/进度/错误存内存（icloudpd/state.ts），经 GET /api/library/:id/sync 与 /api/stats 暴露；数据库仅落 last_sync_at。

5.2 API 清单（已实现，P0 单活跃库：认证全局无库 id，同步按库 id 触发）

方法路径说明
GET/api/libraries库列表（含 active/auth_status/account/目录/照片视频计数）
POST/api/libraries创建库（body {name}；已有激活库时不激活，仅首次建库激活）
PATCH/api/libraries/:id/active切换激活库（同步执行中 409；热切换：停 watcher → 清队列 → 关 DB → 重扫）
DELETE/api/libraries/:id删除库（body {removePhotos}；必删注册 + 缓存目录，removePhotos 才删照片；删激活库自动切剩余库/回默认路径）
POST/api/auth开始认证（spawn icloudpd webui auth-only）→ starting
POST/api/auth/input输入密码/验证码（桥接 webui；inputLock 防重）
GET/api/auth认证状态轮询（starting/waiting_password/submitting/waiting_code/done/error）
POST/api/auth/cancel取消认证（taskkill 进程树）
POST/api/library/:id/sync触发同步：body {kind: full|inc}；仅限当前激活库（其他库 409）
GET/api/library/:id/sync同步任务状态（全局单任务）
DELETE/api/library/:id/sync取消同步任务
GET/api/stats全局统计 + 当前库同步状态（含 libraryId/kind）+ 认证状态 + 缩略图失败/忽略计数
